# Agent provider layer

Status: **approved phase-1 contract; implementation in progress**. Host integration experiments (E-HARDEN, E-PERM-RO, E-STEER-UUID, E-INT-TOOL, E-STEER-WAKE) and the idle-memory load measurement are not yet recorded; their sections below say so explicitly.

The companion talks to coding agents only through a provider layer: one provider trait, one neutral model and declared capabilities. Codex and Claude are two equal providers. Every thread is bound to exactly one provider for its whole life. The client keeps its Codex-shaped wire (protocol `0.155.1` shapes) in phase 1; the companion translates neutral → client wire in exactly one place, and the client hides features that the thread's provider does not declare.

Local ownership rules live with their source zones; this document routes to them and records the cross-zone contract:

- [`packages/agent-protocol/CONTEXT.md`](../packages/agent-protocol/CONTEXT.md) — the `codewide-agent` protocol contract, version policy and fixtures.
- [`crates/agent-core/CONTEXT.md`](../crates/agent-core/CONTEXT.md) — the neutral model (Rust mirror), the `AgentProvider` trait, `NativeSurface` storage traits, neutral usage accounting, `wire-request-ids-v0`.
- [`crates/agent-search/CONTEXT.md`](../crates/agent-search/CONTEXT.md) — the stored-message full-text search schema and query shared by provider adapters (`companion/search`).
- [`crates/agent-index/CONTEXT.md`](../crates/agent-index/CONTEXT.md) — the shared offset index of transcript files (witnesses, turn ranges, incremental scans, watcher), generic over the adapter's record format.
- [`crates/agent-resources/CONTEXT.md`](../crates/agent-resources/CONTEXT.md) — the provider-neutral thread resource model, projection and service shared by provider adapters.
- [`crates/companion-host/CONTEXT.md`](../crates/companion-host/CONTEXT.md) — narrow host contracts the companion hands to adapter crates.

## Scope

Phase 1 delivers the provider layer (`crates/agent-core`, `crates/agent-transport`, `crates/companion-host`, the adapter crates and `crates/companion-core/src/agent`), the neutral protocol package, the Codex adapter as a refactor of today's paths, the Claude provider (a Rust adapter that drives the user's `claude` CLI), binding backfill, capability delivery to the client and the minimal client change set (provider at `thread/start`, same-provider model filter, capability gating, provider badge, approval title, neutral wording).

Not in phase 1:

- switching the provider inside a thread — **dropped** (owner decision, see [Decision: no in-thread provider switching](#decision-no-in-thread-provider-switching)); fork into another agent and cross-provider subagents replace it;
- migrating the client to the neutral protocol;
- ~~moving the Codex storage modules to new paths~~ — done: they live in `crates/agent-provider-codex/src/`;
- review, goals, background terminals, realtime voice, global supervisor, message search and thread resources;
- any Claude account pool (switching, login or removal), or credential handling (live Claude costs are API-rate estimates and finished turns carry Claude's own estimate, see [Token usage and cost](#token-usage-and-cost)); Claude's sign-in and subscription limits are reported read-only (see [Provider status](#provider-status-companionagentprovidersread));
- shipping Claude Code or the Claude Agent SDK with CodeWide (the user installs `claude`; the SDK is not used).

## Shape

```text
Android (Codex-shaped client wire, capability gating)
  └─ /v1 sync ─ SyncHub (sessions, outbox, ingest)
       └─ agent/client_wire  — the only neutral ↔ client-wire translation
            └─ agent/registry + agent/bindings — routing by binding and capability
                 ├─ AgentProvider ─ crates/agent-provider-codex  ─ Codex App Server (in-process adapter)
                 │                   └─ rollout storage + index (crates/agent-index), message search ─ crates/agent-search
                 └─ AgentProvider ─ crates/agent-provider-claude (in-process adapter)
                                     ├─ Claude native index (state.redb tables, watcher), message search ─ crates/agent-search
                                     ├─ thread service + one session actor per live thread ─ stream-json over stdio ─ user's claude CLI
                                     └─ Claude's session store (session records, read and written) + thread state files
```

The registry is built by `crates/companion-core/src/agent/providers/mod.rs` (`build_registry`), the only code outside an adapter crate that maps configured provider ids to adapters. The neutral types and the `AgentProvider` trait live in `crates/agent-core`; the JSONL/WebSocket transports, including the supervised stdio child (`spawn_supervised_stdio`), live in `crates/agent-transport`.

Forbidden edges: provider-id branches in `client_wire` or SyncHub; `registry`, `bindings` or `client_wire` depending on an adapter crate (`agent-provider-codex`, `agent-provider-claude`); SyncHub (`sync.rs`, `sync/*`, `thread_view.rs`, `sync_pending.rs`) reaching Codex storage in `crates/agent-provider-codex` (`history_service`, `resources`, `account_pool`, `rollout*`, `catalog*`, `message_search`) instead of the `NativeSurface` storage traits of the capability owner; `agent-core`, `agent-transport` or an adapter crate depending on `companion-core`; `agent-index` depending on `agent-core`, an adapter crate or `companion-core`; `agent-provider-claude` depending on `agent-provider-codex` or `companion-host`; the client reaching a `claude` process directly.

## Ubiquitous language

- **Provider** — an agent backend implementing `AgentProvider` (`codex`, `claude`; the `ProviderId` set is open).
- **Primary provider** — the configured provider that leads `thread/list` pagination, owns the single default model row and whose threads carry no badge.
- **Binding** — the companion-owned record that fixes a thread's provider.
- **Capability** — a declared, named feature of a provider; the only basis for routing differences and client gating.
- **Neutral model** — the `codewide-agent` v1 types: thread, turn, item, runtime request, events and operations.
- **Client wire** — the existing Codex-shaped v0.155.1 protocol the client speaks in phase 1.
- **Wire projector** — `agent/client_wire`, the single neutral → client-wire translation and client-wire → neutral decoder.
- **Wake turn** — a turn with `origin: provider`, started by the provider without a user message.
- **Busy start** — the `turn.start` outcome `busy {activeTurnId}` for a provider whose thread is already active.

## Neutral protocol `codewide-agent` v1

`packages/agent-protocol` is the source of truth (TypeScript types, capability vocabulary, versioned fixtures). Rust mirrors it with serde under `crates/agent-core/src/model/`; both must round-trip every fixture. Ids are branded in both languages: `ProviderId`, `AppThreadId`, `ProviderThreadRef`, `TurnId`, `ItemId`, `RuntimeRequestId {provider, nativeId}`, `ClientMessageId`.

The model covers `AgentThread`, `AgentTurn` (`origin: user | provider`), the `AgentItem` discriminated union, `RuntimeRequest` (`approval`, `userInput`, `capabilityRequest`), events (`thread.updated`, `turn.*`, `item.*`, `request.*`, `usage.updated`, `plan.updated`, `diff.updated`, `capability.event`) and operations (`initialize`, catalogs, `thread.*`, `turn.start | steer | interrupt`, `request.respond`, `capability.invoke`). The exact shapes are owned by the package, not by this document.

`AgentThread.preview` is the thread's newest conversation message, not its first prompt: the last final answer of the latest finished turn, else the latest agent or user message (user text as the conversation shows it, without model-only context; whitespace collapsed; truncated). Every surface that carries a thread's preview — `thread.list` rows, `thread.read` and the `previewText` of a history invalidation — follows the same rule. Codex projects it from the rollout's latest turn (`enrich_thread_list`, rollout invalidations); Claude from its native index (see [Claude native index](#claude-native-index)).

Ordering rules every provider keeps:

- `turn.started` precedes any item of that turn;
- a `userMessage` is the first item of a user-origin turn;
- every started item is completed before `turn.completed`;
- at most one `agentMessage` with phase `final` per turn;
- `item.completed` carries full content.

Background task reports (added within v1): the item `taskNotification {itemId, delivery: wake | midTurn, kind: agent | command | other, taskId, name, agentThreadId, status: completed | failed | killed | stopped | interim | lost | unknown, durationMs, toolUses, result}` is a report a background task (a sub-agent, a background command, a monitor) delivered to the agent. Every field is always present, `null` when unknown; `agentThreadId` can be non-null only for `kind: agent` (the sub-agent's read-only child thread); `result` is at most 8 000 UTF-16 units. `delivery: wake` reports started a provider-origin turn and are its first items, before any agent item; `midTurn` reports were delivered into a running turn and sit at their delivery position. A report is not agent output: it never releases or demotes the turn's final answer. The wire projector sends it as the CodeWide item `codewideTaskNotification {id, delivery, kind, taskId, name, agentThreadId, status, durationMs, toolUses, result}` (camelCase, nulls kept), in the `full` and the `summary` items view, and the companion's activity metrics never count it. The companion's activity metrics (`companion-host` `activity_metrics.rs`) count all work of a turn without a user message — any provider's, Codex included — as the turn's response: such a turn has no pre-turn part, so items marked `codewidePreTurn` count as response too. Release order: the Android OTA that renders `codewideTaskNotification` ships before the Companion that emits it; an older app shows the item as an unsupported block.

Background task output (added within v1, capability `threads.backgroundTaskOutput`): a person taps a background task — a `command` that started one, or its `taskNotification` — and reads its output in pages, also while it runs; nothing shows an output tail inline.

- Item: `command` carries the optional `backgroundTaskId` (TS `backgroundTaskId?: string`, Rust `AgentItem::Command.background_task_id`; fixture `fixtures/v1/background-tasks.json`), the provider's id of the background task the command started; absent for a foreground command. The wire projector adds it to `commandExecution` as `codewideBackgroundTaskId` only when present and **omits** the field otherwise (never `null`), so a foreground command and every Codex command keep their earlier bytes. A `taskNotification` already names its task (`taskId`, `kind: command` for a background command).
- Operation (optional, `threads.backgroundTaskOutput`): `thread.backgroundTask.read {appThreadId, taskId, offset, limit}` → `{taskId, status, text, nextOffset, sizeBytes}`. `status` is `running | completed | failed | killed | stopped | lost | unknown`: the newest final report's status (an `interim` report is not final), else `running` while the provider's live session knows the task started and has not reported, else `unknown`. `text` is UTF-8 from byte `offset`, at most `limit` bytes (capped at 65 536) and cut on a character boundary; an offset inside a character starts at the next character, and a page holds at least one character even when that character is longer than `limit`. An incomplete last character (a running task is writing it) is left for the next page unless nothing else is left. Bytes that are not UTF-8 read as U+FFFD; offsets always count the file's bytes. `nextOffset` is the exact byte after `text`, `null` when the page reaches the end of the file as it was read; `sizeBytes` is the file size at that moment, so a reader of a running task continues from `sizeBytes`. `AgentProvider::thread_background_task_read` defaults to `-32072`.
- Client wire: `companion/thread/backgroundTask/read {threadId, taskId, offset?, limit?}` (offset absent → 0; limit absent → 65 536, larger → 65 536) → `{taskId, status, text, nextOffset, sizeBytes}` (camelCase, `nextOffset` kept as `null`). It is thread-scoped: the gateway resolves the binding and requires `threads.backgroundTaskOutput` (else `-32072`), and `client_wire/results.rs` runs the neutral operation; SyncHub lists it as a known read outside the ordered lane. Errors: an unknown thread is the existing `-32600 "thread not found: <id>"`; a missing `taskId`, a negative offset or a non-positive limit is `-32602`; a task id that is not 1–64 ASCII letters and digits is `-32602 "invalid background task id"`; a task the thread neither launched nor reported (a sub-agent's read-only child thread has none) is `-32074 "background task not found: <taskId>"`; a known task whose output file is gone or unreadable is `-32074 "background task output is unavailable: <taskId>"`.
- Security: the client never supplies a path. The provider reads only for a task id the thread's own items launched (`backgroundTaskId`) or reported (`taskNotification.taskId`), and only the regular file `<a session of the thread's chain's tasks directory>/<taskId>.output`; the id's shape (letters and digits) cannot name another file. Claude: the tasks directory is `<temp root>/claude-<uid>/<project key>/<session id>/tasks`, with the uid and project key of the session file in Claude's store and the temp root the `claude` children inherit (`CLAUDE_CODE_TMPDIR`, else `TMPDIR`/`TMP`/`TEMP`, else `/tmp`) or the root of the output path the launching call's result names — counted only when that path ends with exactly those components. The directory is canonicalized and must still end with those components, the file is opened with `O_NOFOLLOW` and read only when it is a regular file the session owner owns; a read takes at most `limit` + 6 bytes. Paths are never logged.

The `summary` items view of `thread.turns` (and of every wire turn projected with it) keeps the user messages, the final answer, the sub-agent launches (`subagent`, on the wire `collabAgentToolCall` with tool `spawnAgent` and `codewideDescription`: a client derives the agents a turn started and those still working from them) and the background task reports (`taskNotification`); no other activity item. The rule is defined once, `agent_core::model::turns::in_summary_view`: provider pages (`page_turns`) and the wire projector (`client_wire/items.rs`) both apply it, so anchored history pages, cursor catch-up and sync reconciliation see the same items.

Version policy: changes within v1 are additive only. A breaking change bumps the version and `initialize` negotiates it; a mismatch disables that provider with the `error` log "agent protocol version mismatch".

## Thread bindings

Every thread has an explicit binding, Codex threads included. "No binding means Codex" is never a rule.

- Record: redb table `agent_thread_bindings`, versioned `v:2`: `appThreadId`, `origin: created | discovered | backfilled`, `createdAtMs` and ordered `segments [{provider, nativeThreadId, firstTurnOrdinal, lastTurnOrdinal | null, handoffRefs[]}]`. Each segment is one provider's native thread serving a contiguous run of the app thread's turns; the app thread id is the first segment's native id; routing uses the active (last) segment. The v1 fields (`activeProvider`, `refs {provider → ProviderThreadRef}`) are kept as a copy so a rolled-back companion still routes. v1 records are upgraded once (marker `agent_bindings_segments_v2`).
- Table `agent_thread_continuations`: native threads that are non-first segments of an app thread. Hiding rule: a continuation is never listed, searchable or addressable as its own thread.
- History of an app thread: its segments' native turns in segment order, a closed segment contributing at most its ordinal span (`assemble_history`). Turns and items carry optional `provenance {provider, nativeThreadId}`; adapters stamp it where absent.
- Invariants: exactly one segment; its native id equals `appThreadId`; the provider never changes. The segment model (`agent_thread_continuations`, `assemble_history`, `provenance`) stays as harmless groundwork; nothing writes a second segment, because in-thread switching is dropped.
- Writers, independent of provider identity:
  - **create** — `thread/start` names a provider in `codewideAgentProvider` (absent or `null` → the primary provider, for older clients; an invalid id → `-32602 "codewideAgentProvider is invalid"`); the companion mints a UUIDv7 `AppThreadId` for providers declaring `threads.hostMintedIds`, otherwise takes the provider-minted id; the binding is written before the response;
  - **backfill** — one-time job `agent_bindings_backfill_v1` (durable progress marker per provider) for every provider declaring `threads.externalDiscovery` (Codex and Claude); pages non-archived then archived threads through the neutral `thread.list` (the Codex adapter asks for all source kinds, state-DB only; Claude lists its own and terminal-started sessions), 100 rows per page; restart-safe and duplicate-free. It runs only when the companion is in active mutation mode, starts 30 s after companion startup and then waits until the provider is live;
  - **observation** — every listed row and every `thread.updated` upserts its binding;
  - **discovery on a miss** — a thread id without a binding:
    - exactly one provider declares `threads.externalDiscovery` → the call is routed provisionally to that provider without an extra `thread.owns` call; the `discovered` binding is written only after the provider accepts the call, so a rejected call leaves no binding and the provider's own error reaches the client;
    - several providers declare it (Codex and Claude) → each is asked in registry order via `thread.owns` (Codex, then Claude; Claude answers from its native index first, then from its thread service); the first owner gets a `discovered` binding before the call is routed;
    - no provider declares it, or none owns the id → `-32600 "thread not found: <id>"`.
- An upsert never changes an existing binding's provider. A conflicting claim is logged at `error` and ignored.
- `thread_metadata.model_provider`, model ids and id shape are never used for routing.

## Capabilities

Each provider declares its capability set at `initialize`. The registry indexes them.

Client-wire extensions are attached only when more than one provider is enabled (`ProviderRegistry::is_multi_provider`). A Codex-only host therefore keeps today's client wire byte-for-byte. In multi-provider mode:

- every projected `Thread` — RPC results (`result.thread`, `thread/list` and `companion/supervisor/threadList` rows), `thread/started`, and durable replay of notifications projected in this mode — carries `Thread.codewideAgent {provider, providerName, primary, capabilities}`: the bound provider id, its display name (badge text only), whether it is the primary provider (no badge) and its declared capability set. The TypeScript shape is `CodewideAgentThreadExtension` in `packages/agent-protocol`;
- `model/list` and `permissionProfile/list` carry the `codewideAgentProvider` / `codewideAgentProviders` annotations described below.

A thread without `codewideAgent` (single-provider or legacy companion) is treated by the client as a Codex thread with every capability. A `codewideAgent` that is present but malformed is not legacy: the client reads it as an agent with no capabilities (provider unknown when its id is unusable) and logs it once (`thread_agent.descriptor.malformed`).

Routing and degradation, by capability only:

- A thread-scoped call resolves the binding (discovery first), then requires the capability its client-wire method maps to. Missing → `-32072 "<capability> is not supported by this thread's agent"` with `data {capability, provider}`, without contacting the provider.
- A connection-scoped call (`config/read`, `fs/*`, `skills/list`, `plugin/*`, realtime start, account methods) goes to the registry's owner of the matching host capability (`host.fs`, `host.config`).
- `model/list` in multi-provider mode: every row carries `codewideAgentProvider`; the first page appends other providers' rows after the primary provider's rows; exactly one `isDefault` (the primary's); at most 100 rows; a duplicate model id keeps the earlier provider's row. Non-primary rows are labelled `"<Provider> · <displayName>"`. With one provider the response is unchanged.
- `permissionProfile/list` in multi-provider mode: every row carries `codewideAgentProviders` (the providers offering it); profiles offered only by non-primary providers are appended. With one provider the response is unchanged.
- Missing catalogs (multi-provider mode only): when a non-primary provider is not live or its catalog call fails, the first `model/list` page and every `permissionProfile/list` result carry `codewideAgentProvidersUnavailable: [providerId]` (absent when every provider answered). The client does not treat such a catalog as fresh: it keeps that provider's previously cached rows and refreshes again on the next load. A Codex-only host never adds the field.
- Account limits: `accounts.rateLimits` means the Codex account-pool limit wire (`account/rateLimits/read`, `account/rateLimits/updated`, `companion/accountPool/*`). The client shows pool account rows and reads the account pool in a thread's header only when the thread's provider declares it (a legacy thread keeps them). In multi-provider mode the account section is titled with the pool owner's provider name ("Codex accounts").
- Provider-level subscription limits without an account pool are not a capability: a provider entry of `companion/agentProviders/read` carries `rateLimits` (null until the first report) exactly when the provider reports them (Claude, from `rate_limit_event` frames and the `get_usage` control request). The client shows them in that provider's account row and in the usage menu of its threads' header ("unknown" until the first report); other threads keep their context usage only.

### Provider status: `companion/agentProviders/read`

- `companion/agentProviders/read {}` (answered in every mode) → `AgentProvidersReadResult` (`packages/agent-protocol/src/v1/providers.ts`; producer `crates/companion-core/src/agent/provider_status.rs`):

  ```text
  {providers: [{id, name, primary, status: live | reconnecting | unavailable | disabled,
                auth: authenticated | unauthenticated | unknown, planLabel: string | null,
                accountLabel?: string, rateLimits?: ProviderRateLimits | null,
                capabilities: CapabilitySet | null}],
   hostCapabilities: {<boolean capability>: bool}}
  ```

  Enabled providers come in registry order (primary first), then disabled ids (`capabilities: null`). `status` combines the transport (`ProviderStatus`: live, reconnecting) with the provider's health (`ProviderHealth::Unavailable`, for example a protocol version mismatch). `auth`, `planLabel` and `accountLabel` come from `ProviderHealth::Available(ProviderAuth)`; a provider that reports nothing (Codex) is `unknown`. `accountLabel` (the signed-in email, else organization) is present only while signed in with a reported label; `rateLimits` is present only for a provider whose adapter reports provider-level limits (`AgentProvider::subscribe_rate_limits`), so a Codex-only read result keeps its earlier bytes. `hostCapabilities` names every boolean capability with `true` when some enabled provider declares it, so connection-scoped features (global voice mode: `realtimeVoice`) are known without probing for `-32072`; the client keeps the `-32072` handling as fallback.
- `companion/agentProviders/changed` — a durable journal notification whose params are the full read result, emitted only in multi-provider mode whenever a provider's status, sign-in state, capabilities or subscription limits change. A Codex-only journal is unchanged (its status keeps reaching the client as the session `status` frame).
- The client shows the list in the server detail screen as provider status ("Claude · signed in · Max", "Claude · not signed in — run `claude` on the server to sign in"), and a provider without an account pool as a read-only account row in Accounts under its own section ("Claude": "Signed in via Claude Code on <server>" with the account label and plan, or "Not signed in — run `claude` on the server"; no switching, login or removal), only when the server lists more than one provider. A companion without the method answers `-32601`; the client records it as unsupported and renders as before.
- Sign-in state never carries credentials: the Claude adapter derives `{authenticated, label, accountLabel?}` (label = the plan type; accountLabel = the email, else organization, of an Anthropic login, shown like a Codex pool account's email and never logged) from the `initialize` answer of its runtime probe (`runtime/probe.rs`, a short-lived `claude` that makes no model call) and publishes it as the provider's health. The neutral notification `account.updated {account}` (fixture `fixtures/v1/account-updated.json`) stays in the protocol.
- Subscription limits: the provider → companion notification `rateLimits.updated {rateLimits: ProviderRateLimits}` (fixture `fixtures/v1/rate-limits-updated.json`) always carries the provider's full merged snapshot `{updatedAt, windows: [{id, kind: session | weekly | other, label, windowDurationMins, usedPercent (integer 0–100) | null, resetsAt (Unix seconds) | null, status: allowed | warning | rejected | null}]}`, ordered session, weekly, then other ids. The Claude adapter (`live/rate_limits.rs`) merges windows by id from `rate_limit_event` frames (`rateLimitType` names the window; a frame without a usable window or figure is ignored) and from `get_usage` control requests, taken by the probe and, after a turn's result, at most once per two minutes through a live session; a failed or unrecognized usage read changes nothing. The adapter publishes the latest snapshot; the companion lists it on the entry. The adapter probes again (at most once per minute) on a catalog read while no model is known or the user is signed out, so a sign-in on the server reaches the client without a restart.
- Thread pins are companion state, not agent storage: `thread_pins.rs` stores them in the companion store and SyncHub annotates `codewide.threadPin {version, pinned, cursor}` on `result.thread` and on `thread/list` / `companion/supervisor/threadList` rows of every provider; a pin read failure returns `-32020 "Thread pin projection unavailable"`.
- Clients decide features only from `codewideAgent.capabilities`, never from model ids or provider names. The provider name is used only as badge text.

## Decision: no in-thread provider switching

Owner decision: a thread never changes its provider. Switching inside a thread (the former phase 2: more binding segments plus a context handoff on every switch) is dropped. Two features replace it:

- **Fork into another agent** — the user forks a thread into a new thread on another provider; the new thread starts from a context handoff and the source thread is unchanged.
- **Cross-provider subagents** — the model of any thread starts, waits for, messages, cancels and lists agents on any enabled provider through companion-owned orchestration tools.

The tools reach the model as **client-side tools over the existing provider channels** (Codex `dynamicTools` / `item/tool/call`; Claude: an in-process MCP server answered over the `claude` process's own stdio control protocol), not through a standalone MCP server or an HTTP endpoint: no extra process, port, token or auth surface; the caller's identity is the channel that carried the call and the thread it names (which must be bound to that channel's provider), never a credential in the arguments.

## Orchestration tools

Declared by the companion, identical for every provider (`crates/companion-core/src/agent/orchestration/tools.rs`). Results are JSON text content (the JSON-encoded result object); failures are unsuccessful tool results (`success: false` with a clear message), never JSON-RPC errors. The main agent decides whether delegation is useful; CodeWide supplies durable tools and safety policy, not a second coordinator agent or an autonomy setting.

| Tool | Arguments | Result |
|---|---|---|
| `codewide_delegate_task` | `{prompt, waitMode: "blocking" \| "deferred", provider?, model?, name?, permissionProfile?, workspace: {mode: "sharedReadOnly", cwd?} \| {mode: "isolatedWrite", sourceWorkspace?}}` | accepted task snapshot with `taskId`, `attemptId`, `provider`, `model`, status and, after binding, `agentThreadId`; or a typed pre-admission rejection |
| `codewide_wait_task` | `{taskId, timeoutSeconds?}` (default 60, maximum 300) | snapshot of that task's authoritative first attempt; a returned terminal fallback is acknowledged atomically |
| `codewide_cancel_task` | `{taskId}` | task snapshot after an idempotent cancel intent; `cancelling` is not `cancelled` |
| `codewide_spawn_agent` | `{prompt, provider?, model?, name?, cwd?, permissionProfile?}` | `{agentThreadId, provider, model, status: "running"}` |
| `codewide_wait_agent` | `{agentThreadId, timeoutSeconds?}` (default 60, clamped to 300) | `{status: "running" \| "completed" \| "failed" \| "interrupted", finalMessage?, turnId?}` |
| `codewide_send_agent` | `{agentThreadId, message, mode?: "queue" \| "steer"}` (default `queue`) | `{status: "running" \| "queued"}` |
| `codewide_cancel_agent` | `{agentThreadId}` | `{status}` |
| `codewide_list_agents` | `{}` | `{agents: [{agentThreadId, provider, model, name \| null, status \| null, taskId?}]}` |

- **Delegate** creates one durable `OrchestrationTask`, one authoritative `TaskAttempt` and one dedicated child thread. The task covers only the child's first turn; later `send_agent` turns do not reopen or replace its result. Task identity is persisted before child creation or dispatch. An uncertain provider-minted create/start outcome becomes `startUncertain` with the same durable ids and `recovery: "waitTask"`; it is neither a terminal failure nor permission to retry.
- **Workspace and admission**: `sharedReadOnly` forces the target to read-only. `isolatedWrite` obtains its effective directory only through `workspace.create@1` and fails when isolation is unavailable; it never falls back to shared write. The model cannot pass provenance, a permission ceiling, `explicitUserRequest`, `sharedWriteExplicit` or a grant id. The host derives `agentSelected` provenance from the authenticated tool-call context and freezes the caller's permission ceiling before creating the task. Translation may narrow that ceiling but never widen it; unknown translations fail closed.
- **Task states**: the external projection is `running`, `startUncertain`, `cancelling`, `succeeded`, `failed` or `cancelled`. Internally task outcome and completion-delivery acknowledgement are separate discriminated state machines with separate compare-and-set transitions. The first terminal task result wins; delivery failure never reopens or changes it. Unknown provider cost is `null`, never zero.
- **Admission results**: a rejection before the journal write creates no task and uses `capability_unavailable`, `permission_denied`, `workspace_unavailable` or `provider_unavailable`. After admission, every result carries `taskId` and `attemptId`; `agentThreadId` appears only after durable child binding.
- **Wait**: `wait_task` always follows `taskId → authoritativeAttemptId → providerTurnId`, so a later child turn cannot change its answer. A blocking delegate waits no longer than the caller turn; ending the caller turn stops only that wait, not accepted child work. The compatibility `wait_agent` continues to observe the child thread's current turn and never reads or acknowledges task delivery.
- **Send**: `turn_delivery` is the sole owner of every prompt-bearing initial, user-queued or follow-up command and of its durable command-state transitions. It reserves the initial prompt before a child exists, promotes that reservation into the existing durable turn outbox after binding and owns idempotency, queue mutation, provider dispatch, claims, receipts, retry scheduling, history reconciliation, the 1 MiB command limit and the 256 MiB owner quota. Atomic task admission uses the transaction-scoped initial-turn reservation API exposed by `TurnDelivery`: that API owns the write transaction and private prompt-bearing reservation write, runs the journal's prompt-free coordination writer in the same transaction, then commits or rolls both sides back together. `TaskJournal` receives only the stable command id and cannot import the reservation DTO or `turn_delivery_tables`. `sync/queue.rs` only translates `companion/queue/*` DTOs into `TurnDelivery` calls; `turn_delivery/pump.rs` drives provider delivery inside the same owner. Sync and orchestration do not access outbox or reservation storage operations directly. `IndexStore` supplies atomic persistence primitives/schema but owns no queue or retry policy. The orchestration journal stores only stable command references and coordination metadata; it never persists command params or a second prompt copy. `steer` remains explicit and needs the running turn.
- **Cancel**: `cancel_task` records intent against the authoritative attempt; completion may still win the race. The compatibility `cancel_agent` remains an interrupt of the child thread's current turn and cannot rewrite a task.
- **Scope**: a tool addresses only children of the calling app thread; anything else is `agent not found: <id>`.
- **Surfaces**: delegated agents are ordinary threads (listed, openable) and are added to `companion/threadSubagents/read` of their actual parent (descendants included) in the indexed-subagent row shape, also for parents whose provider lacks `subagentThreads`. The compatible child projection may add `taskId`; task state, delivery state, permission envelopes and orchestration events never cross into client wire. Their tool calls render in the parent as `dynamicToolCall` items with the bare tool name.
- **Durability and data boundary**: the orchestration journal owns task, attempt, closed-kind metadata event, workspace-claim reference and fallback-delivery coordination records. It never stores a prompt-bearing command, transcript, final answer, account label, URL, credentials or arbitrary provider payload. Initial and follow-up prompts live only in `turn_delivery`/the existing outbox; final content remains in provider history and is read from the authoritative provider turn when returning a result. The persistence regression check decodes the orchestration tables and rejects any prompt text or command params there.
- **Legacy spawn safety mapping**: `codewide_spawn_agent` preserves its existing model-facing arguments, mandatory result fields and error surface, then the host maps the validated legacy call into the safe workspace union before durable admission. Missing `permissionProfile` or explicit `:read-only` becomes `sharedReadOnly` at the explicit absolute `cwd` or the authenticated parent's cwd. An explicit write-capable profile becomes `isolatedWrite`, with that path used only as `sourceWorkspace`; the parent-ceiling and provider-translation checks still apply, and lack of `workspace.create@1` fails closed. The compatibility path never newly admits `LegacyShared`, never inherits writable shared access and never treats model-selected `cwd` as shared-write authority. Any future shared-write compatibility path requires a separate host-minted grant from a user-owned surface, bound to the authenticated parent and approved cwd/permission ceiling. The legacy DTO cannot carry or mint that grant, and this slice implements no such path.
- A passive (read-only shadow) companion declares no tools.

### Durable state ownership

- `OrchestrationTask` is the task identity and terminal authority. `Admitted` may enter `PreparingWorkspace`, `Starting` or pre-start `Cancelled`; `PreparingWorkspace` may enter `Starting`, `Failed` or pre-start `Cancelled`; `Starting` may enter `Running`, `ReconcilingStart` or `Cancelling`; `ReconcilingStart` may enter `Running`, `Failed` or `Cancelling`; `Running` may enter `Succeeded`, `Failed` or `Cancelling`; `Cancelling` may enter `Cancelled`, `Succeeded` or `Failed`. Only `Succeeded`, `Failed` and `Cancelled` are terminal. `ReconcilingStart` projects as `startUncertain` and can become `Running` only when the original provider identity is matched, or `Failed` only when the provider proves execution absent.
- `TaskAttempt` owns the execution binding. Before child binding it has neither child nor provider-turn id; after binding the child id is required; after acknowledged start the provider turn id is required. Independent nullable fields that admit impossible combinations are forbidden.
- `TaskEvent` is append-only metadata with a task-local sequence and one closed kind: `admitted`, `workspaceReady`, `childBound`, `turnQueued`, `turnStarted`, `startUncertain`, `cancelRequested`, `attemptTerminal` or `taskTerminal`. Wall-clock order and late events never choose or replace the terminal outcome.
- `CompletionDelivery` is currently the fallback-only machine `Pending → AwaitingResume → Acknowledged`. A task becoming terminal creates fallback delivery work; `wait_task` acknowledges it after returning the terminal snapshot. No delivery transition changes task state. Native reservation and reconciliation states are not implemented.
- `WorkspaceClaim` records the workspace service claim and effective cwd. Completed isolated workspaces become `retained`; orchestration has no release, reset, clean or delete operation in this slice.

### Compatibility and rollout

- `codewide_spawn_agent`, `codewide_wait_agent`, `codewide_send_agent`, `codewide_cancel_agent` and `codewide_list_agents` are `keep_temporarily`, backend-owned compatibility facades. Their existing inputs, mandatory result fields and error messages stay fixed. They may be removed only after persisted Codex tool specs and supported Claude sessions have stopped calling them for one release window. `spawn_agent` is a deferred facade over durable delegation; the task-addressed tools do not redefine the thread-addressed tools.
- The `spawn_agent` facade's compatibility promise covers its public DTO/result/error surface, not unsafe shared-write semantics. Its host-side mapping is fixed: omitted/read-only profile → `sharedReadOnly`; explicit write-capable profile → `isolatedWrite`; host-granted shared write remains unavailable to model calls. Negative checks reject a newly admitted `LegacyShared` task, writable shared profile inheritance and using an alternate cwd as shared-write authority.
- The v1 parent/child link remains a read-only `public_exception`: old links are not backfilled with synthetic tasks and remain openable/listed. `multiAgentMode: "explicitRequestOnly"` stays an unchanged upstream compatibility field; tool availability, not a new autonomy preference, enables agent-selected delegation.
- The host-owned `delegateTaskEnabled` admission gate is checked before any task, attempt, workspace claim, delivery or prompt reservation is written. When disabled it rejects only new `codewide_delegate_task` admission; already accepted tasks remain recoverable through `wait_task` and `cancel_task`, and the five compatibility tools remain available.
- Completion delivery is fallback-only in the implemented runtime: both Codex and Claude advertise `orchestration.externalDelivery: false`, every terminal deferred task becomes durably `awaitingResume`, and `wait_task` or the child chat remains the recovery surface. The additive capability name is reserved for a future provider-native port, but there is no implemented `nativeCompletionDeliveryEnabled`, native reservation or native reconciliation path.
- A provider may advertise native completion only in a future approved slice after a pinned-runtime probe proves non-user authority, idle and active behavior, restart persistence and delivery-id deduplication, and after source and tests add the native delivery states. Capability vocabulary alone is not evidence that this route exists.

Other requests are forwarded unchanged.

- The server request `item/tool/call {threadId, turnId, callId, namespace, tool, arguments}` for a declared tool with `namespace: null` is answered by the companion with `{contentItems: [{type: "inputText", text}], success}` and never reaches the client; its `serverRequest/resolved` is dropped too. Every other `item/tool/call` keeps today's path. With the tools installed, the recorded golden stream stays byte-identical (`codex_golden_tests`, `codex_tools_tests`).

### Claude wiring

A session offers them to `claude` as the MCP server `codewide` (`--mcp-config` with `type: "sdk"`), which `claude` reaches through `mcp_message` control requests; the adapter answers the MCP handshake and `tools/list` itself (`cli/mcp.rs`).

A failed tool is an MCP `isError` result, never a JSON-RPC error. ## Fork into another agent

- `thread/fork` accepts optional `codewideAgentProvider`, `model`, `serviceTier` and `config.model_reasoning_effort` (the Codex `ThreadForkParams` fields; an empty string is absent), and `codewideInitialPrompt`. Without `codewideAgentProvider` the request and behavior are exactly today's.
- **Same provider** (the field names the thread's provider, or no field): the extension fields are removed. A provider with the native surface runs today's native fork (Codex `thread/fork`, which keeps `model`, `serviceTier` and `config`). A provider without it runs the neutral `thread.fork {appThreadId, forkAppThreadId, boundary}`: the boundary comes from `lastTurnId` (through) or `beforeTurnId` (before); the copy is bound like a created thread, announced with `thread/started` and `forkedFromId`, and the requested `model`, effort and service tier that differ from the copy's settings are applied in one `thread.update` (none when nothing differs). Claude writes the copy into its session store itself, with the semantics of the SDK's `forkSession` (`native/write.rs`, `fork_cut.rs`, `fork_copy.rs`): every session of the chain up to the boundary is copied with fresh message uuids, so the copy owns its sessions and keeps the full transcript.
- **Different provider**: both providers must declare `threads.crossProviderFork` (else `-32072`); it means only that the provider can be a fork source (neutral `thread.turns`) and target (neutral `thread.create`) — ordinary operations, served by the companion. The companion reads the source thread's neutral history (up to 500 recent turns, cut at `lastTurnId` / `beforeTurnId`), creates a new thread on the target (`cwd`; `permissions` from the request else the source's effective named profile or observed sandbox, translated to the target's permission-profile catalog, with unknown access failing closed to `:read-only`; `model` from the request else the target's default; effort and service tier from the request else the target's defaults, never the source's) and answers with the projected thread carrying `forkedFromId`. The source thread is unchanged.
- **Handoff**: a size-capped replay of user and agent messages, commands and file changes (default 16 000 bytes, cap 64 000; the latest request and answer and the original request are kept first; oversized items are omitted whole), ported from t3code `handoffBudget.ts` (MIT, attribution in `agent/fork/handoff.rs`). It is stored durably (`agent_thread_forks`) and prepended as a text input to the user's first `turn/start` of the new thread (direct or queued), until a turn of that thread has started; with `codewideInitialPrompt` the first turn starts at once with the handoff and the prompt. While that first message is pending, the target inherits the source title (or its preview/fallback when untitled): this is a durable metadata mutation, so Codex materializes the otherwise empty rollout and `thread/resume` can open it without a synthetic model turn. The handoff is part of the eventual user message in the target's history.

## Token usage and cost

- `usage.updated` is emitted with every complete model request while a turn runs, and once more when the turn ends; `last` is the latest model request (the context size the client's context fill reads, `latestRequest / modelContextWindow`), `total` the thread's cumulative usage. `TokenUsage.inputTokens` counts every prompt token including cache reads (`cachedInputTokens`) and cache writes (`cacheWriteInputTokens`, added within v1). The optional `cost` (`ProviderCost {basis: list | managed, model, turnUsd, threadUsd | null}`) is a provider's own estimate, sent only when it knows the price table; `threadUsd` is `null` once any turn's cost was unknown. The optional `model` (added within v1) names the model that served `last`; the companion prices that request with it.
- A finished turn read back (`thread.turns`, an index read) carries the optional `AgentTurn.usage` (`TurnUsageRecord {last, turn, total, contextWindow, cost?}`) the provider reported for it; reads never emit `usage.updated`. The wire projector turns it into the same `codewide.usage` turn metadata a Codex history read carries (`TurnUsageProjection::from_record`).
- Claude: the adapter measures each turn as the difference of the CLI's cumulative per-model `modelUsage` totals (main loop, Task subagents, sidechains and compaction; `result.usage` is main-loop only) against the session's persisted checkpoints, including results that do not end the turn (steer aborts, task notifications); `reasoningOutputTokens` are `thinkingTokens`; costs are the `costUSD` differences of models whose `costBasis` is not `unknown`. Restart, zeroed-result and unknown-baseline rules are owned by `crates/agent-provider-claude/src/live/usage.rs`.
- Prices come with the model list: `catalog.models` carries optional `prices` (model id → `ModelPriceEntry {pricingVersion, rates, longContext?}`, USD per million tokens for input, cache reads, cache writes and output; `longContext` is a second rate card above an input size), covering every id a thread setting or a request may name, catalog aliases included. Each provider's table is the shared `CatalogPricing` (`agent_core::usage`), so every provider is priced by the same arithmetic: Codex publishes its `OpenAI` API rates, the Claude adapter its Anthropic API rates (`runtime/prices.rs`); the Claude adapter refreshes its table from every successful runtime probe that returns prices.
- Claude live usage: the adapter reports each complete top-level request (the next request, a tool result or a compaction completes it; one request may arrive as several assistant messages with the same id) with its model and the thread totals including it, and the context window Claude last reported for the thread, else the model's known window (`live/usage.rs`, `model_context_window`). The companion prices these requests from the catalog rates; the turn's final `usage.updated` carries Claude's measured totals and its own cost, which replaces the estimate.
- Pricing in the companion: a thread is priced only by its own provider's table (the provider recorded per thread from its event stream); a provider-reported cost becomes a `CostProjection` with `basis: "providerReported"` (total only, `pricingVersion` = the provider's price table) and is journaled as a pricing input (`codewideProviderCost` on the client-wire `thread/tokenUsage/updated`, `ReplayPricing.providerCost`), never as a derived price. `sync/replay.rs` reconstructs prices for live delivery and catch-up using the thread's durable provider binding; a legacy unbound event uses the host's primary only when exactly one provider is enabled. Native storage adds catalog metadata after pricing and preserves the computed costs. A Codex-only host's wire is unchanged.

## Live thread activity

While a turn runs, the thread list shows what the agent is doing now instead of the thread's preview. The companion derives it from the Codex-shaped client wire both providers share, so it costs no model call and no provider-specific branch (Claude's paid `agentProgressSummaries` and `tool_use_summary` stay off).

- Owner: `crates/companion-core/src/thread_activity.rs` (`LiveActivityTracker`), a per-thread reducer that ingest runs on every notification before content projection. Sources: the first closed `**bold**` header in the first 512 characters of each reasoning summary part; `item/started` of a command (first line of its parsed command), file change (first path and the count of other files), MCP or dynamic tool, web search or context compaction; the plan step in progress from `turn/plan/updated`. The newest signal wins: any started item replaces the previous signal (an item without a label clears it), and the plan step in progress shows when no newer signal remains. `turn/started`, `turn/completed` (interrupted or failed included) and a non-`active` `thread/status/changed` clear it.
- Claude: `PlanStep.activeForm` (optional, added within v1) carries `TodoWrite`'s present-tense label; the wire projector sends it as the CodeWide plan step field `codewideActiveForm`, which the reducer prefers over `step`. Codex plan steps have no such field.
- Wire: `codewideThreadPatch.operation.liveActivity` (`thread_patch.rs` owns the patch shape) is present only on the notification that changed the activity: an object `{kind: reasoning | planStep | command | fileEdit | tool | webSearch | compacting, …}`, or `null` when cleared. The value is journaled with the patch, so replay reproduces every change; a client that resumes from a snapshot starts with none until the next change. The contract is listed under `threadProjectionPatch.liveActivity` in `crates/companion-core/contract/v1.json`.
- Client: `packages/sync-client/src/live-activity.ts` validates the field (an unreadable value clears); Android keeps it in the process-lifetime Legend owner `apps/android/src/data/threadLiveActivity.ts` (never persisted, cleared by a connection snapshot or removal) and the thread row renders a localized label with the text shimmer only while the row is running, else the preview.

## Delivery, steer and interrupt

- Neutral `turn.start` never steers implicitly. A provider whose thread is active and declares `turns.startWhileActive: busy` returns `busy {activeTurnId}`; the companion puts that outbox command back in the queued state ("deliver after idle") and redelivers it once on that thread's `turn.completed`. The client sees an ordinary queued item through `companion/queue/changed`.
- `nativeJoin` (Codex) keeps today's App Server behavior: the adapter reports `started` with the joined turn id, so Codex wire behavior is unchanged.
- Steer is only an explicit `turn.steer {expectedTurnId}`; a mismatch returns `-32600 "expected turn is not active"`.
- `turn.interrupt` answers `{}` within 1 s when a turn is active, already interrupted, completed or the thread is idle; it errors only for a foreign `turnId` during an active turn or an unknown thread. Open requests resolve with `request.resolved` before `turn.completed`. Repeats never hang.

## Error codes

- `-32070 "<Provider> provider is disabled on this host"` — terminal (`Rejected`, then `Failed`).
- `-32072 "<capability> is not supported by this thread's agent"`, `data {capability, provider}`.
- `-32020 "Thread binding is unavailable"` — the binding store could not be read or written while resolving a thread-scoped call (logged at `warn` with `err`).
- A configured Claude that cannot start on this host (see [Install and configuration](#install-and-configuration)) answers `-32070` like a disabled one; its status is `unavailable`.
- `-32600 "native session not found: <id>"` — a native session read of a session the provider's store does not have (in process; no provider answers `nativeSession.*` over RPC any more).
- `-32074 "background task not found: <taskId>"` / `"background task output is unavailable: <taskId>"` — `companion/thread/backgroundTask/read` of a task the thread neither launched nor reported, or whose output file is gone (see [Neutral protocol](#neutral-protocol-codewide-agent-v1), background task output).
- `-32073 "thread not found: <id>"` — `companion/thread/sync` of a thread the companion does not know or its provider no longer has (for example deleted elsewhere). The client removes the thread locally and closes it if it is open.
- `-32602 "<model> is a <Provider> model; this thread runs on <Provider>. Fork the thread to switch agents."` — `turn/start`, `thread/settings/update` or `turn/settings/update` of an existing thread names a model that only another enabled provider lists (multi-provider mode; catalogs cached for 5 minutes, re-read once for an unknown model). A model no catalog lists stays with the thread's provider. A queued turn fails once with the same message.
- `-32071` is not used: there is no session cap.

## Codex sub-agent threads

The backend owns a sub-agent thread's content; the client renders it as served. A Codex sub-agent child (`session_meta.source.subagent.thread_spawn` in the first record of its rollout) is a thread of its own turns only:

- A child spawned with the parent's turns (`fork_turns` other than `"none"`) starts with a copy of the parent's history inline in its rollout — the parent's `session_meta`, a `compacted` record and parent turns under the parent's turn ids. Its first `session_meta` names `forked_from_id` and `subagent_history_start_ordinal`, the zero-based index of the record its own history starts at (Codex 0.161 and later). The companion resolves that record's byte offset once per rollout (`rollout_origin.rs`) and serves no turn that starts before it: sync resets and deltas, `thread/turns/list` summary and `notLoaded` pages, `companion/thread/history/before|after`, thread-list previews and rollout invalidation previews. A copied turn id is unknown to the child (an anchor on it is an expired cursor).
- A child naming `forked_from_id` without the ordinal (older CLIs) owns the turns whose UUIDv7 id is no older than the child's own UUIDv7 id; the cut applies only when both ids are UUIDv7. A child without `forked_from_id` copied nothing and owns every turn.
- A child never continues another rollout: inherited bases (`history_base`) are followed only for paginated user forks, which keep their inherited history.
- The history source witness of a child with a cut carries `excludes_inherited`; a witness issued while the copy was served lacks it, so a client that cached the copied turns gets one reset.
- Full item views and the active turn are the App Server's (`thread/turns/list` with `itemsView: full`, `thread/items/list`): for a paginated child it serves them from its own thread history projection, which starts at the child's own records (checked on 0.161.0 and 0.162.1 children against App Server 0.163.0), so the companion does not filter them.
- Thread metadata comes only from a rollout's first record: the parent header copied into a child never overwrites the parent's thread-index row.

## Claude provider

The Claude provider is one crate, `crates/agent-provider-claude` (Rust only). It drives the user's own `claude` CLI directly over its stream-json protocol; there is no separate host process and no Claude Agent SDK. The former TypeScript host (`host/`, package `@codewide/claude-agent-host`, before that `apps/claude-sidecar`) is removed; the adapter keeps its on-disk thread state and its observable protocol behavior.

- **Process model.** The adapter runs in the companion process. One session actor (a tokio task) per live thread owns the thread's state, its `claude` process and its active turn. A process is started per session with the command line the SDK built for a streamed query (`cli/command.rs`) and spoken to over stdio: user messages, the control requests `initialize`, `interrupt`, `set_permission_mode` and `get_usage`, and Claude's control requests `can_use_tool` and `mcp_message` (`cli/protocol.rs`, `cli/process.rs`). A short-lived probe process that answers only `initialize` reads the account, the model list and the plan's usage (`runtime/probe.rs`).
- **Session lifecycle.** `Shell` (hidden from the non-archived list until the first user message) → `Active` ↔ `Idle` → `Released` (idle release, or companion shutdown: input closed, up to 10 s for `claude` to exit on its own) → resumed on the next turn; a lost session is recovered with a new session id and a bounded transcript prefix (up to 16 KiB under `[Historical conversation from this thread]`, built from whatever history Claude's store still has for the thread); a second loss in the same turn fails it.
- **Idle release.** After 30 min without activity (configurable 5–240 min); never while a turn is active or a request is pending; background tasks defer release up to 4 h.
- **No session cap.** One idle `claude` process costs about 125 MB PSS (research probe P2), and idle release bounds the steady state. Without a cap, a killed `claude` process fails only its own active turn ("Claude process exited unexpectedly"); its open requests resolve, the session becomes `Released` and the next turn resumes it. The adapter logs the live session count at `info` on every open and release. The companion memory watch reads only the companion main PID, so `claude` children do not trigger its alerts.
- **Permission profiles.** `:read-only` restricts built-in tools to Read/Glob/Grep/LS, disables settings sources and MCP, and denies everything else in `can_use_tool`; `:workspace` accepts edits with user/project/local settings and asks for the rest; only `:full-access`/`:danger-full-access` bypasses permissions; an unknown profile returns `-32602 "Unsupported permission profile for Claude: <id>"`. A profile change between `:workspace`, `:full-access` and `:danger-full-access` takes effect at once, also inside a running turn (`set_permission_mode` on the live process; a process started without `--allow-dangerously-skip-permissions` keeps its mode and `can_use_tool` allows every tool while the thread's profile is full access); a change to or from `:read-only`, and model or effort changes, apply at the next turn boundary. The thread reports the chosen settings (`pendingSettings ?? settings`) in `thread.updated` as soon as they change. A client-wire `turn/start` carrying `model`, `effort` or `permissions` (a new chat sends them only there) becomes a neutral `thread.update` settings change before `turn.start`.
- **Approval decisions.** `accept` → allow; `acceptForSession` → session-scoped permissions only (never a settings file); `decline` → deny; `cancel` → deny with interrupt. A `can_use_tool` request is always answered; a decline or response error never becomes allow. A sub-agent's request (`agent_id`) is decided the same way, but its call is never an item of the conversation's turn (its result reaches only the sub-agent's transcript), and it wakes a provider turn only when the user must answer it or it calls a client tool.
- **Credentials.** No CodeWide component reads, stores, forwards or logs Claude credentials, tokens or `ANTHROPIC_*` values. Auth state comes only from the `initialize` answer of the runtime probe (the plan type and the account's email or organization, never a token or key source); subscription limits come only from `rate_limit_event` frames and `get_usage` answers. From the user's Claude `settings.json` the adapter reads only the standard proxy variables of `env`. The watcher reads only directory entries and size/mtime under `$CLAUDE_CONFIG_DIR/projects` (or `~/.claude/projects`); session records are read and written by the adapter's `native` and `transcript` modules. Claude's costs are its own estimates (see [Token usage and cost](#token-usage-and-cost)).
- **Logs.** Full errors in `err`; opaque ids allowed; prompts, outputs, tool inputs and env values never logged.

### History and thread list from Claude's session store

The Claude provider is symmetric with Codex: Codex's adapter crate owns rollout storage, a rollout parser and a native index; Claude's adapter crate (`crates/agent-provider-claude`, Rust) owns its native index in the companion's `state.redb`, a watcher on Claude's session files, and the parser of Claude's session format (`transcript/`), which maps stored messages to neutral items. The adapter keeps no conversation copy; its thread service keeps only per-thread metadata Claude's store cannot hold.

#### Native session reads

The index reads Claude's sessions in process through `native::LocalSessions`, which returns the shapes of the optional `nativeSession.list` / `nativeSession.read` operations typed in `packages/agent-protocol` (`NativeSession`, `NativeSubagent`; fixture `fixtures/v1/native-sessions.json`). No process answers them over RPC any more; the types and fixture stay as the index's contract.

- `nativeSession.list {dir: string|null, cursor: string|null, limit}` → `{sessions: NativeSession[], nextCursor}` — every session whose working directory is `dir`, or of all projects, programmatic and interactive, newest first, at most 500 per page; a session another listed session continues is hidden. `NativeSession {sessionId, appThreadId, cwd, title, summary, firstPrompt, createdAtMs, lastModifiedMs, fileSize, interactive}`: `appThreadId` is the session id, or the CodeWide thread a replacement session continues; `lastModifiedMs` and `fileSize` let the index detect a change cheaply; `interactive` marks sessions a person started (terminal, IDE). The cursor (`v1:<offset>`) is opaque; a store change between pages may shift entries, which a re-index tolerates.
- `nativeSession.read {sessionId}` → `{session, turns: AgentTurn[], subagents: NativeSubagent[]}` — one session as neutral turns, rebuilt as below, plus each sub-agent transcript (`<session>/subagents/agent-<agent id>.jsonl`) as `{agentId, parentAgentId, parentToolUseId, turns}`, sorted by `agentId`; `parentToolUseId` links it to the spawning tool item. Ids depend only on the stored messages and the thread's turn index: turn id = the turn index's turn id or the uuid of the turn's first stored message; items `{turnId}:user:{n}`, `{message.id}:{block}`, `tool_use.id`, `{tool_use.id}:image`, the compact-boundary uuid. Reading unchanged input twice returns equal results, so re-indexing is idempotent. A turn still running in the session is returned as its live snapshot (`inProgress`); after `turn.completed` the companion re-reads and re-indexes. Unknown session: `-32600 "native session not found: <id>"`.
- `NativeSession.codewide` (optional; omitted for a session CodeWide never touched) carries every `thread.list` row field Claude's store cannot hold: `{createdAt, cwd (the CodeWide thread's working directory, where its turns run), origin: "interactive" | "external", presence: {type: "listed", archived} | {type: "deleted", deletedAt}, recencyAt: number | null, settings: ThreadSettings (effective: pending settings when set), title: {type: "none"} | {type: "pending", name} | {type: "cleared", hiddenTitle}, updatedAt}` (unix seconds). The row name is the latest session title of the thread, replaced by `title.name` when `pending`, and `null` when `cleared` and the store title equals `hiddenTitle`. Tombstoned threads whose session still exists are listed with `presence.type: "deleted"`, never silently dropped. Every session of a chain carries the same object.
- Each session's `turns` hold only that session's share of its thread: a replacement session after a lost session starts with the resent prompt (history prefix removed, the original turn id and `clientMessageId`) and never repeats earlier turns. If the old session still exists in the store, the interrupted turn appears in both sessions under the same turn id; the later session's share is the continuation.
- Every turn and item the adapter emits or returns (live events, `thread.turns`, native session reads) carries `provenance {provider: "claude", nativeThreadId: <appThreadId>}` (phase 1: the Claude thread is its only native thread).
- Live turns keep streaming as events; `thread.list`, `thread.read` and `thread.turns` keep working from Claude's store until the companion serves them from its index.

- `thread.list`, `thread.read`, `thread.turns` and `thread.owns` read Claude's own session store directly: the listing reads the head and tail of each session file as Claude's own listing does (`native/meta.rs`), a read rebuilds a session's active branch (`transcript/chain.rs`). `thread.update` name and delete write the store (`native/write.rs`): a rename appends a `custom-title` row; a removal deletes the session file and its directory.
- Listed threads are CodeWide's own threads plus every session a person started outside CodeWide (for example, `claude` in a terminal or an IDE), with the session id as thread id, `origin: external` and default settings (`model: default`, `:read-only`) until changed. Programmatic sessions (an SDK entrypoint or a daemon) are not listed unless CodeWide owns them. `thread.list` semantics are unchanged: params, the `v1:<sortKey>:<direction>:<valueSec>:<id>` cursor, the sort keys (`recencyAt` falls back to `updatedAt`), windows, search over name else first prompt, and shells hidden from the non-archived list. Every listing rescans Claude's store; the companion's native index owns any longer-lived cache. On the client wire every non-native row carries that order key as `recencyAt` (its `updatedAt` when the thread has no recency of its own), never `null`: a client that persists `recencyAt` as a sort column would otherwise order such threads after all others.
- Name: Claude's session title (`/rename`, a `custom-title` row CodeWide appends, or Claude's generated title). A name given before Claude created the session is kept in the thread state and appended once the session exists; clearing a name (Claude cannot) hides the current title in the thread state. Repeats emit `thread.updated` only on a real change.
- Delete writes a tombstone to the thread state, then removes every session of the thread's chain from Claude's store; a session Claude no longer has counts as deleted, a failed removal is logged at `error` and retried by a repeated delete, and repeats always answer `{thread: null}`.
- The adapter keeps only metadata Claude's store cannot hold (`<journalDirectory>/threads/<id>/state.json`, version 2, the format the former host wrote, so existing threads keep their ids; owner `src/state/`): the session chain, settings and pending settings, the archive flag, the tombstone, a title override, cumulative usage and a turn index (turn id, origin, outcome and error, prompt uuids with their role and `clientMessageId`). `active-turn.json` holds the in-flight turn's snapshot until it ends, so a companion restart finalizes it as interrupted. No conversation content is stored. A v1 journal of the former sidecar is converted on first start (its copied turns are left on disk unused and can be deleted).
- History is rebuilt from the stored messages of the session chain and replayed through the live `TurnBuilder`, so turns and items have the live ids, types, ordering and final-answer rule. A user turn's id is the uuid of its first prompt offer, which Claude persists. Turn boundaries are derived: a prompt starts a user turn unless the index knows it as a steer or a resent prompt, or Claude queued it (`isQueuedCommand`) into a running turn; a task-notification or peer message starts a provider turn unless Claude queued it into a running turn; `[Request interrupted by user…]` ends a turn as interrupted; the first persisted message of every CodeWide-driven turn starts that turn. The active turn is served from the live snapshot.
- Person vs. harness messages: interactive Claude Code stamps a person's prompts `origin: {kind: "human"}` (SDK- and stream-json-driven sessions store none); they are `userMessage` items with their text and image blocks. Messages with another `origin.kind` (task notifications, peer messages) are wakes and never `userMessage` items. Injected meta messages (`is_meta`: reminders, skill bodies) and command/markup echoes (`<command-name>`, `<local-command-stdout>`, `<system-reminder>`…) are hidden, not rendered as notices.
- Sub-agents: an `Agent` (formerly `Task`) call is a neutral `subagent` item (added within v1: `description`, `prompt`, `agentType`, `model`, `background`, `result`, `status: running | completed | failed | stopped`, `agentThreadId`), projected as Codex `collabAgentToolCall {tool: spawnAgent}` whose status stays `inProgress` while the agent runs, with the CodeWide field `codewideDescription` (the `Agent` call's short description, always a string; the client's agent display name). Its child thread id is `<app thread id>:agent:<agent id>`, from the spawning result (`tool_use_result.agentId` live, the `agentId:` line in both) or `task_started`. Live, a `task_notification` frame finishes the item of the running turn; history applies every later `<task-notification>` of the same conversation level, so a background agent finishing after its turn shows its final status after the next re-index. A native session read keeps the last turn of a sub-agent its spawning item still reports `running` in progress. A child thread's `AgentThread.spawn` names its parent (the parent sub-agent's thread for a nested one), its description and agent type; the wire projects them to `parentThreadId`, `agentNickname`, `agentRole` and `canAcceptDirectInput: false`, so a client that reads the child files it under its parent instead of listing it as a root.
- Background task reports (`taskNotification` items, see [Neutral protocol](#neutral-protocol-codewide-agent-v1)), read by `transcript/task_reports.rs` and mapped by `transcript/task_notifications.rs`: history reads every `<task-notification>` of a task-notification wake (`task-id`, `tool-use-id`, `status`, `summary`, `note`, `result`, `usage` `duration_ms`/`tool_uses`); a result is opaque up to its last `</result>` before its notification's closing tag (the first after the result that ends the message or precedes the next notification), so a notification or `<usage>` quoted inside a result is neither a report nor the report's usage. A report Claude queued into a running turn is stored as a `queued_command` attachment with `commandMode: task-notification`; the session file's active branch (`transcript/chain.rs`) delivers it as a queued user message with that origin, and it becomes a `midTurn` item at its position. The reports of the wakes before a provider turn's first message are its `wake` items, in order; wakes buffered before a prompt are `midTurn` items after that prompt; wakes an interrupt marker ends before any message of their own make an interrupted provider turn whose id and end are the marker's (live, that turn ran with the reports leading it until the interrupt). Reports are carried beside a segment's stored messages (`transcript/segments.rs`), so turn ids, start anchors, turn ends and fork cut points are those of the turn's own messages: the same session with every report a plain peer wake rebuilds the same turns and fork ends. Kind and name come from the summary (`Agent "X" …`, `Background command "Y" …`, else `other` named by the summary, `Background task` without one), the name cut to 200 UTF-16 units; status is `lost` when the summary says the task did not finish before the previous session ended, `interim` when the note says the result may be interim, else the reported `completed`, `failed`, `killed` or `stopped`, else `unknown`; `result` is the trimmed text cut to 8 000 UTF-16 units on a character boundary. Item ids are `{turnId}:notification:{n}`. Live (`session/task_reports.rs`), a `task_notification` frame of a task the main conversation started (not a task a sub-agent owns — `owned_by_subagent` or `spawn_depth` above 1 on its `task_started` — and not a foreground call still open in the turn, whose result carries the outcome) becomes a `midTurn` item while a turn runs (a `wake` item while a provider turn has no item yet); while idle it waits and the next turn delivers it once — `wake` items leading a provider turn, `midTurn` items after a user turn's prompt or, in a `/compact` turn, after its compact boundary, where history has them; reports waiting when the query ends are dropped, and a report never starts a turn by itself. Live differences: an agent is named by its `task_started` description, a live report carries no result text and no note (so no `interim` status), and a report Claude received during a turn but answered in the following wake turn is a `midTurn` item of the running turn live and a `wake` item of the following turn after the next re-index. The index logic version 7 rebuilds indexed histories with these items. A background `Bash` call's `command` item carries the task id of its structured result (`toolUseResult.backgroundTaskId` stored, `tool_use_result` live; an id without Claude's shape is dropped); index logic version 8 rebuilds indexed histories with it. The live session keeps, per open query, the tasks it saw start (`task_started`) and the status of every report it received, which answers `running` for an output read (`session/task_reports.rs`).
- Child threads: the adapter indexes each sub-agent's turns (`claude_subagent_turns`) and publishes a companion thread-index row under its parent (nickname = description, role = agent type); `companion/threadSubagents/read` of a thread without the `codex.native` surface reads that tree. `companion/thread/sync` carries the same tree as `subagents` (`null` when it cannot be read), read after the snapshot's history, and the companion journals `companion/thread/subagents/invalidated {threadId}` for every `SubagentsChange` (`take_subagent_changes`) once the index holds the new rows, so a client re-reads the tree whether the thread is open or not. `thread.read` / `thread.turns` / `thread.owns` of a child id are answered from the index (read-only; the thread is `active` while the agent runs); the thread service has no thread for them.
- Lost in history compared with live: reasoning text (Claude stores only thinking signatures; reasoning items keep their ids with empty summaries), Bash stdout/stderr split (the tool result text is used), applied patches (file diffs are rebuilt from Edit/MultiEdit/Write input; a `Write` over an existing file shows as `add`), tool durations other than tool_use → tool_result timestamps, MCP server names when they contain `__` (the init frame is not stored), and — for sessions CodeWide did not drive — `clientMessageId` echoes, failed outcomes and steer grouping. If Claude's store loses a session, its history is gone too, and a replacement session gets only the prefix the store still allows.

### Discovery of sessions started outside CodeWide

- Claude declares `threads.externalDiscovery` (`CAPABILITIES`). A terminal-started session becomes a thread when it appears in a merged `thread/list` page or a `thread.updated` event (observation), through the one-time backfill over Claude's `thread.list`, or on a miss: discovery asks Codex then Claude via `thread.owns`; Claude answers from its native index first, then from its thread service, which owns any session in Claude's store that is not another thread's continuation.

### Claude native index

- `thread.list`, `thread.turns`, message search and thread resources of Claude threads are served from the companion's Claude native index; the thread service (reading Claude's store directly) answers until the index is fresh. The provider-neutral thread resource model, projection and service live in the shared crate `crates/agent-resources`; Codex keeps its rollout reading and its own store.
- Freshness: the index serves `thread.list` only after a listing pass matched the thread service's listing, while no turn runs and no re-read is pending; a `thread.updated` the index would list differently triggers a collapsed re-pass. Deleted threads are dropped from list, search and `thread.owns`. Turns are de-duplicated by turn id across a thread's sessions (the later session wins).
- Known gaps: a CodeWide thread with no session file yet, and a first prompt Claude has not written yet, are not in the index list (the thread service answers during running turns anyway). Merged search treats a failing provider index as a failed source and errors only when every source fails.

- Symmetric with Codex's rollout index: the Claude adapter crate derives disposable tables inside the companion's index database — `claude_sessions` (session id → indexed session), `claude_session_turns` (session id + ordinal → one neutral turn) and `claude_thread_sessions` (app thread id + session id) — versioned by `claude_index_logic_version` (a change drops and rebuilds them). A thread's metadata row (and its sub-agent child rows) takes the newest session's directory: the CodeWide thread's `cwd`, else the session's own; a listing leaves a session's `cwd` unknown when the file's first `cwd` lies past the head it reads, which must not keep the thread out of the index.
- Watcher: filesystem events under Claude's projects directory trigger a debounced rescan, plus a periodic 30 s rescan. It compares each session's `fileSize` and `lastModifiedMs` from the native listing (the file's byte size and floor of its mtime in ms) with the index and re-reads only changed sessions.
- Indexer: backfills every listed session with a native session read, re-reads a session after a change or after `turn.completed` of a live turn, and removes sessions that left the store. CodeWide thread metadata from `NativeSession.codewide` is published to the companion's thread index, so the catalog and thread list are served from the index; tombstoned sessions (`presence.type: "deleted"`) are dropped there.
- Freshness rule: the index serves `thread.turns` only when the thread has no running turn and no pending re-read; otherwise the call goes to the thread service.
- Preview: each indexed session stores the preview of its newest message (a turn without any message yields to the turn before it); a thread's preview is that of its newest session holding one, else its first prompt. The thread service projects only the first prompt, so the adapter overlays the indexed preview on every `thread.list` row and `thread.read` the service answers; a thread not indexed yet keeps the service's first prompt (then its only message). A watcher change published as a history invalidation carries the thread's indexed preview as `summary.previewText`.
- Message search: the adapter writes indexed turns into `claude-message-search.sqlite` using the shared `crates/agent-search` schema (`documents::replace_thread`). `companion/search` routes to every provider declaring `history.messageSearch` and merges results in the shared order (newest first, then thread id, then the later position); continuations are never search results.

### Install and configuration

- Shipping: nothing Claude-specific is built, embedded or installed with CodeWide: no host executable, no Node.js or Bun, no Claude Agent SDK, no separate installer. The user installs and signs in to the `claude` CLI. Codex stays required: a Claude-only host (no Codex app-server) is not supported, because Codex is the primary provider built from the `serve` flags.
- On start the companion removes the former host's files (`legacy_install.rs`): the former installer's directories (Linux `~/.local/lib/codewide/claude-agent-host` and `…/claude-sidecar`, macOS `~/Library/Application Support/CodeWide/ClaudeAgentHost`), `<state dir>/claude-agent-host` and `<state dir>/claude-agent-sdk`.
- Config file `<companion state dir>/agent-providers.json` (Linux `~/.local/state/codewide/companion`, macOS `~/Library/Application Support/CodeWide/Companion`): `version: 1`, `primary: "codex"`. Without a `providers.claude` entry Claude runs whenever the companion finds `claude` (on the user's login-shell `PATH`, the companion's `PATH`, `~/.local/bin`, `~/.claude/local`, `/opt/homebrew/bin`, `/usr/local/bin`); `"claude": false` turns it off. An entry object overrides any field, all optional: `claudeExecutable`, `journalDirectory` (default `<state dir>/claude-journal`), `idleReleaseMinutes` and `environment`. The former host's fields `hostExecutable`, `agentSdk`, `runtimeExecutable` and `sidecarEntry` are accepted and ignored.
- `environment` holds only `PATH` (absolute directories, no empty entry) and `CLAUDE_CONFIG_DIR` (absolute); any other key, including `ANTHROPIC_*`, makes the entry invalid. A service manager starts the companion with a minimal `PATH`, while Claude's Bash tool inherits the `PATH` of its `claude` process; without `environment.PATH` the adapter asks the user's login shell (`$SHELL -l -c 'printenv PATH'`, bounded to 5 s) and falls back to the companion's own `PATH`. Every `claude` process gets `PATH` = the directory of `claude`, then that `PATH`; `CLAUDE_CONFIG_DIR` when configured; and the proxy variables (`HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY` and their lowercase forms) the user's Claude `settings.json` sets in `env` (the managed policy tier is applied by `claude` itself). An unreadable or invalid `settings.json` leaves Claude unavailable rather than starting it without the user's proxy. The watcher observes `<CLAUDE_CONFIG_DIR>/projects` from the same entry (else the companion's `CLAUDE_CONFIG_DIR`, else `~/.claude/projects`).
- File absent, unreadable or invalid → Codex only, built from the existing host flags (an unreadable or invalid file is logged once at `error`); the registry is still built and holds one provider. An invalid `providers.claude` entry or an unknown provider id → only that provider is disabled, with one `error` log. The primary provider must serve the merged client surface (`thread/list`, `model/list`, `permissionProfile/list` pass through its `codex.native` surface): a configured `primary` that is not enabled or lacks that surface is logged at `error` and Codex leads instead.
- `registry.rs` parses the file with opaque per-provider entries; the mapping from a provider id to its adapter lives in `crates/companion-core/src/agent/providers/mod.rs` (`build_registry`), so the registry never imports an adapter.
- `codewide-companion providers status [--state-dir <dir>]` (Linux) prints the providers as JSON — config state, each provider's status (`builtIn`, `ready`, `notReady` with problems, `disabled`, `off` with the reason Claude does not run, `invalid`, `unknown`), the effective `PATH` of the `claude` processes and the watched session store — and exits non-zero unless every configured provider is ready. It is offline: it reads the config and file metadata (and the `#!` line of `claudeExecutable`, resolving an `env` interpreter on that `PATH`), starts no process and makes no model call.
- Logs: every host installs the shared filter (`companion_core::log_filter`): `warn` for all targets, `info` for the companion, `companion_core::agent`, `agent_transport` and the provider adapters; `RUST_LOG` directives refine it per target instead of replacing it. Linux logs to the journal; macOS writes `~/Library/Logs/CodeWide/companion.log` (rotated at 8 MiB into `companion.log.1`).

#### systemd hardening (Linux, E-HARDEN)

`claude` and every Bash tool command are children of `codewide-companion.service` and inherit its sandbox (Codex tools run under the separate app-server). Measured with transient units carrying the unit's hardening (systemd 255): `os.networkInterfaces()` fails with `EAFNOSUPPORT` without `AF_NETLINK`; bubblewrap (Claude's sandboxed Bash) fails with "No permissions to create new namespace" under `RestrictNamespaces=true`, and with `--unshare-net` also needs `AF_NETLINK`; `claude --version` itself runs. Because Claude runs by default, the unit itself (`apps/companion-linux/deploy/codewide-companion.service`) adds `AF_NETLINK` and allows the namespace types bubblewrap creates (`user mnt pid net ipc uts cgroup`); the former `claude-provider.conf` drop-in is gone. `ProtectSystem=full` stays: a `claude` installed under `/usr` cannot update itself while CodeWide runs it (update it from a shell). `NoNewPrivileges` and the empty capability bounding set stay.

## Rollback

- Triggers: any Codex golden-replay diff or Codex regression; a Claude permission bypass.
- **Disable Claude:** remove `providers.claude` from `agent-providers.json` and restart the companion. Claude models leave the picker, calls on Claude threads return `-32070`, queued Claude commands fail once, Claude rows leave the list. Bindings and the Claude thread state stay; nothing is deleted.
- **Revert the layer:** revert the C3 switch-over commit. The old single-upstream route returns. The binding table is ignored and needs no reverse migration.
