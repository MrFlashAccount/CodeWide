# Forge

## Purpose and owner

`forge/` is the companion's bounded context for forge pull requests. It owns providers, account links and auth flows, PR identity, plugin selection and calls, the action-run journal, PR–thread links, agent scenarios and branch detection. It serves the `companion/forge*` and `companion/pullRequest*` RPC families through `ForgeService`. The plugin contract is [`docs/forge-plugins.md`](../../../../docs/forge-plugins.md); the conversation contract is [`docs/forge-conversation.md`](../../../../docs/forge-conversation.md).

Code owner: backend. This document: architect.

Deleting this module removes every PR surface; review targets that do not involve a forge stay in [`review/`](../review/CONTEXT.md).

## Module jobs

- `mod.rs` — `ForgeService`: dispatch of `companion/forge*` and `companion/pullRequest*`; claims every such method before the App Server fallback, even with every provider disabled.
- `ids.rs` — branded newtypes and their validation: `PullRequestKey` (`fpr1.<base64url>` over plugin id, host, repository, number; opaque to Android), `ForgeAccountKey` (plugin id + host + login), `HeadRevision`, `AuthFlowId`.
- `providers.rs` — the provider list: compiled-in built-ins plus external entries; durable enable flags.
- `bundled.rs` — the built-in descriptors (plugin id, bundled binary, priority; no name, host or icon) and resolution of `bundled:<id>` at every spawn against the host-supplied bundled plugin directory; a missing binary is "provider unavailable", never a fallback path. The VCS registry resolves its built-in `bundled:git` against the same directory through its own `vcs/bundled.rs`; the two plugin APIs share the directory, not a provider list.
- `identity.rs` — each provider's display identity as its plugin last declared it in `initialize` (`forgeName`, `defaultHost`, `providerIcon`): recorded by every session, the icon resolved once per distinct declaration, kept in memory and in `forge_provider_identities` so a disabled or unstarted provider keeps it; a provider that never initialized shows its plugin id and no icon. An unreadable icon source is retried after 10 minutes and never stored.
- `icons.rs` — the single validator of provider icons: a declared glyph, inline image, file (relative to the plugin executable) or `https` URL becomes an inline glyph or image, or `None`. The companion fetches URL icons itself so a client never contacts a third-party host.
- `registry.rs` — `forge-plugins.json` v1: external plugins (`id`, absolute canonical `executable`, `args`, `priority`), atomic writes, built-in ids reserved.
- `directory.rs` — `companion/forge/accounts/read`, `companion/forge/provider/setEnabled` and `companion/forge/account/setEnabled`: provider descriptors with the declared identity (`forgeName`, `icon`), `defaultHost`, sanitized auth methods and derived account states; a provider that cannot start degrades only its own card. The account switch changes only the link's durable `catalogEnabled` flag and never calls a plugin. Every card carries `installation` (`installed`, `missing` or `failed` with a short reason), recomputed on each read; `providers.rs` logs a missing executable once per provider id.
- `accounts.rs` — account links (no tokens) with their `catalogEnabled` flag (kept across re-verification and repeated sign-in), account state derived from `auth.verify`, `unlink`, `forgetToken` and confirmed `logoutHost`.
- `auth.rs` — auth flows: start, one dedicated plugin process per flow, poll every 5 s, cancel, 15-minute expiry reported as `failed` with a reason, and a terminal `failed` flow kept until dismissed, restarted or 15 minutes pass; `submitToken` handled before any journaling.
- `plugin_client.rs` — spawn, `initialize`, capability check, timeouts, bounded concurrency. Uses `forge-protocol` framing; the VCS plugin client is not refactored.
- `cache.rs` — in-memory list, overview and conversation-page cache with freshness windows; a pull request invalidation drops all three. No PR content on disk.
- `declarations.rs` — each provider's last `initialize` declaration (capabilities, sanitized `mediaHosts`), refreshed by every session, so media routing decides without a spawn per image.
- `conversation.rs` — `companion/pullRequest/conversation/read` (`forge.conversation@1`): the validating adapter of `ConversationPage` (bounded page and cursor, ids checked, permalinks `https` on the PR host, avatars `https`, direct `media` URLs and `avatarDirect` only `https` on the provider's declared `mediaHosts`; threads with an impossible anchor dropped, an invalid `reviewId`, iteration or issue `changedAt` nulled, issue `changedBy` checked like every author), cached like the overview; `thread_location`/`thread_state` name a thread's anchor and resolution for the focused scenario context; `find_thread` pages (at most 20 pages, never the cache) to one review thread for a focused scenario.
- `comments.rs` — `companion/pullRequest/comment/create` and `companion/pullRequest/reviewThread/reply` (`forge.comments@1`): body bound, journal replay, capability check, `started` journal, the plugin call with the trimmed body, `outcomeUnknown` for a local failure, PR invalidation after any outcome that may have written.
- `media.rs` — routes a media URL whose host is a connected account's host, its subdomain or a declared media host of a `forge.conversation@1` provider through `forge.media.read`; refusals fall through to the next account and finally to the anonymous fetch.
- `attention.rs` — hashes a provider activity witness and durably records the exact revision last displayed for each PR; list and overview reads expose only the content-free digest plus `new | seen`.
- `review_chat.rs` — durably assigns one canonical ordinary agent thread to a PR. One resolution (`resolve`, under one companion-owned lane) serves both `chat/ensure` and the `reviewChat` scenario target: the stored canonical thread while it is live, else a live linked thread (branch links first), else a newly created and linked thread; the choice is stored as canonical. `chat/ensure` never enqueues a message or starts a turn.
- `chat_workspace.rs` — where a new canonical review chat runs. A client opts in with `workspace` on `chat/ensure` or on the `reviewChat` scenario target: `{"kind": "ask"}` returns `{"kind": "needsWorkspace", "candidates": [{path, reason}]}` (reason `pullRequestBranch` or `repository`, head-branch checkouts first, the first is the client's default, an empty list offers none) instead of creating a thread while no live canonical or linked thread exists; `{"kind": "path", "path"}` creates it there after workspace admission, with `:workspace` only when that directory passes the same match as a candidate (the branch-linked checkout, or a probed directory `match_reason` accepts), else `:read-only`. Candidates are the branch-linked checkout, then up to 32 project roots, then up to 16 recent distinct indexed thread `cwd`s (for example an `arc-wt` worktree an agent ran in), probed with `vcs.remotes@1` (4 at a time, 10 s each). A probed checkout is a candidate only when the PR provider's `forge.repository.resolve` maps its remotes to the PR's host and repository; it is `pullRequestBranch` when its local branch or its upstream (tracking) branch equals the PR's head branch, else `repository`. Without `vcs.remotes@1` on the workspace's VCS provider or `forge.resolve@1` on the PR's forge provider nothing is probed as a checkout: only the branch-linked checkout is offered, and a chosen directory gets `:read-only`. Without `workspace` the older behavior and result shape stay: the local checkout, else a `:read-only` thread in the companion home.
- `reads.rs` — the legacy cross-account list, provider-aware structured search, the atomic overview, activity pages, file pages with hunk catalogs and viewed marks; one plugin process per provider batch.
- `pr_catalog.rs` — the pull request implementation of review's `DiffCatalogSource`.
- `actions.rs` — catalog validation, kind floors, the `forge_action_runs` journal.
- `action_run.rs` — `companion/pullRequest/action/run`: idempotency replay, fresh catalog at the requested head, effective confirmation, journal, then the plugin call.
- `submit.rs` — Submit review over `review::DraftStore`.
- `links.rs` — PR–thread links (`branch`, `manual`, `agent`), tombstones, local-checkout resolution.
- `detection.rs` — demand-driven branch detection: `vcs.remotes@1`, then `forge.repository.resolve`, then `forge.pullRequests.byBranch` for the upstream (tracking) branch and then the local branch when it differs (a checkout may track the PR's server branch under a local name of its own).
- `scenarios.rs` — `fixCi`, `rebase`, `addressComments`, `reviewPr`, `message`; the only target is `{"kind": "reviewChat"}` (the PR's canonical review chat, resolved by `review_chat.rs`), workspace admission, untrusted context input. The retired `thread` and `newThread` targets are rejected: no client picks among linked threads or adds another thread for a scenario.
- `scenario_runs.rs` — per-intent scenario idempotency and live state. A slot is (PR, scenario kind, target: `checkId` for `fixCi`, `reviewThreadId` for a focused `addressComments`); `message` has no slot. Admission runs inside the review chat lane: a start whose slot has a queued or running run at the same head joins it (same `threadId`, nothing enqueued); another head, or a finished, failed or unknown run, queues a new run that replaces the slot record. `companion/pullRequest/scenarios/read` derives each slot's `idle | queued | running | done | failed` from the recorded settlement, else the outbox command and then its turn (no plugin call, no prompt or answer text). A `turn/started` or `turn/completed` on a run's thread publishes `{"scope": "scenarios"}` for its PR; a turn end records the settlement.
- `tools.rs` — the `codewide_link_pull_request` client tool host.
- `limits.rs` — page sizes, timeouts, concurrency, freshness windows and auth flow timing. Android renders flags and does not restate these numbers. Guide limits are owned by `review/guide`, because review must not import forge.
- `ids.rs`, `wire.rs`, `errors.rs` — branded ids; the companion → client shapes; the `-32080..-32089` error model and the plugin-code mapping.

Composition outside this folder, each with one job:

- `sync/forge_rpc.rs` — constructs the forge and review services, claims their RPC families before any App Server forwarding, feeds thread lifecycle events to detection, and installs `ForgeService::route_media` as the media path's `PrivateMediaSource` (`SyncHub::route_forge_media`, called by each host). `media.rs` defines that trait and never imports `forge`.
- `agent_bridge.rs` — hands turns to the existing durable outbox, creates threads with an explicit permission profile, reports a thread as live, archived or missing (stored catalog state for native-storage providers, the provider's thread read otherwise; a native thread with no stored history yet is live only while its runtime still holds it, see `unmaterialized_threads.rs`) and reads a turn's final message; it never names a provider.
- `server/forge.rs` — admin routes `/v1/forge/providers` used by the Linux `forge provider` CLI.
- `store/kv.rs` — lazily created `&str → bytes` tables used by `forge_tables.rs` and `review_tables.rs`; `store/thread_cwds.rs` looks up thread `cwd`s in the companion thread index for workspace admission and lists recent distinct ones for review chat candidates.
- `vcs/remotes.rs` — the optional `vcs.remotes@1` call; a provider without it answers `None`. `OrderedRemotes` orders the returned URLs for detection; the value types live in `companion_host::vcs`.
- `untrusted.rs` — the single owner of fencing third-party text as data for agent prompts, shared by forge scenarios (`scenarios.rs`) and the review guide catalog (`review/guide/catalog.rs`). Rules:
  - each block's fence is a run of `~` longer than any `~` run in its body, so no body line can close it;
  - attribute values lose quotes, line breaks and control characters and are cut to 200 characters, so they cannot end the opening line or the attribute;
  - all block bodies of one section share one byte budget; a body is cut to the remaining budget, and a block with nothing left to show is dropped.

  Forge and review never hand-roll fencing; every third-party text an agent sees goes through `UntrustedText`.

Durable state lives in `store/forge_tables.rs`: `forge_accounts`, `forge_provider_settings`, `forge_provider_identities`, `forge_pr_links`, `forge_link_tombstones`, `forge_action_runs`, `forge_pr_attention`, `forge_pr_review_threads`, `forge_scenario_runs`. Tables are additive and created lazily on first write.

## Invariants

- **No token in the companion.** A forge token is never returned by a plugin, never stored in redb, `SecureStore`, the journal or logs, and never sent to Android. The only token that crosses the companion is the `submitToken` param, passed unchanged to the plugin's `auth.start` stdin and dropped; it is excluded from the replay journal, the outbox and request logging.
- **One trigger per forge write.** Review comments and the verdict: only `companion/pullRequest/review/submit`. Catalog actions: only `companion/pullRequest/action/run` with `confirmation` at or above the effective level (`-32089` otherwise). Viewed marks: only `companion/pullRequest/viewed/set`. A conversation comment: only `companion/pullRequest/comment/create`. A review thread reply: only `companion/pullRequest/reviewThread/reply`. Both publish immediately, as on the forge itself; line comments on the diff remain drafts that reach the forge only through Submit review. Attention: only `companion/pullRequest/attention/seen`, after the matching overview revision was displayed. Auth flows: only `companion/forge/auth/start` from a device-authorized session. No agent tool, scenario or refresh path constructs an action run or starts an auth flow.
- **Attention is revision-exact and content-free.** A provider witness is hashed before storage or client projection. Opening revision A never marks a later revision B as seen. Recording a marker invalidates the server list cache but does not push a list invalidation to the active client, so a row cannot move between attention groups while its detail remains open.
- **Opening chat is not sending.** `companion/pullRequest/chat/ensure` reuses the PR's live canonical thread or creates and links exactly one. It never calls the agent enqueue path; only an explicit composer submission or scenario starts a turn.
- **No silent directory for an opted-in client.** With `workspace: ask`, neither `chat/ensure` nor a scenario start creates a thread when no live canonical or linked thread exists; it answers `needsWorkspace`. A scenario answers it before journaling, so the start after the choice is not a replay. Once a live chat exists it is returned and any choice is ignored.
- **One conversation per PR.** Every scenario started from a PR goes to the same canonical thread `chat/ensure` returns. Archived or missing threads are never canonical or reused; an archived or missing canonical thread is replaced by a live link or a new thread, which is stored as canonical. A thread is missing only when that is proven: no route knows it, or Codex has neither a rollout nor a runtime holding it (a chat opened but never written to, after an App Server restart or idle unload). An unreadable thread state fails the request instead of replacing the canonical thread.
- **Search is complete or rejected.** `companion/pullRequests/search` sends the same typed query to every selected account. A provider without `forge.search@1` may receive only the exact legacy projection supported by `forge.list@1` (category, zero or one repository, open state and default sort); any richer query fails the read. The companion never drops an unsupported condition and returns a broader result set.
- **Stale head.** Every run and Submit carries `headRevision`; a moved head returns `-32082` with a refreshed catalog and writes nothing.
- **Idempotency.** A run (action, Submit, scenario, comment, thread reply) is journaled as `started` before the plugin call. A repeated `idempotencyKey` returns the stored terminal outcome without a plugin call; a timeout or restart in `started` ends as `unknown` (`-32083 outcomeUnknown`). A scenario is also deduplicated per intent: a new key for a slot whose run is queued or running at the same head returns that run's thread instead of enqueuing another (`scenario_runs.rs`).
- **Effective confirmation** = max(plugin `confirm`, kind floor), recomputed here and never trusted from the client.
- Account state (`connected`, `expired`, `error`) is derived and never stored; `connecting` is an auth flow.
- An account with `catalogEnabled: false` is skipped by `companion/pullRequests/list` and `search` only. Overview, detail and media reads of its pull requests are unchanged, and branch detection and PR–thread linking deliberately keep using it: excluding an account hides it from the catalog, not from the threads that work on its pull requests. `companion/forge/provider/setEnabled` is the administrator's rollback (Linux CLI); Android has no provider on/off.
- At most one active auth flow per provider and host.
- Forge refresh is demand-driven only: client reads (60 s freshness, coalesced per account and category), `thread/started` and `turn/completed` of a VCS workspace thread (30 s debounce per workspace), and link mutations. No poller, no PR watch.
- A `branch` link is never re-added when a tombstone for that PR and thread exists. Detached HEAD makes no link; only open PRs are linked.
- `codewide_link_pull_request` writes only companion link state for the calling thread and never writes to a forge.
- Third-party PR text reaches an agent only as a separate fenced untrusted input with its source and authors. A focused `addressComments` (`reviewThreadId`) carries only that thread: its comments, path, lines, side and state.
- **No forge media token in the companion.** Forge-hosted images are fetched by the plugin (`forge.media.read`) inside its own allowlist; the companion receives bytes, applies the media path's own size, type and cache rules, and never logs the URL. Credential-free direct URLs a plugin hands out in `Comment.media` pass to the client only on declared media hosts and are never downloaded, logged or journaled by the companion (write acknowledgements drop them).
- `overview.localCheckout.workspace` is derived only from project roots and known thread `cwd`s, so it always passes workspace admission.

## Dependency rules (`must_not_import`, checked in review)

- `forge` may import `review`, `vcs`, `workspaces`, `store` and `forge-protocol`.
- `review` must not import `forge`; forge implements review's `DiffCatalogSource` for PR files.
- `crates/agent-*` and `crates/companion-host` must not import `forge`, `review` or `forge-protocol`.
- Forge plugin crates (`crates/forge-github`, external plugins) must not import `companion-core`; they depend only on `forge-protocol`.
- No `match`/`if` on a plugin id or forge name outside `providers.rs` and `bundled.rs`; behavior branches on capabilities and descriptor kinds. No provider's display name, host or icon is compiled into the companion; they come from the plugin's `initialize`.
- `vcs.rs` and `vcs/plugin.rs` change only by the optional `vcs.remotes@1` call; VCS framing and ownership paths stay unchanged.
- Provider fallbacks in the companion are forbidden. Forge and VCS behaviour of a particular provider (Arc, Arcanum, GitHub, …) lives in its plugin and reaches the companion only through declared capabilities (`vcs.remotes@1`, `forge.resolve@1` with `forge.repository.resolve` and `forge.pullRequests.byBranch`, …). When a plugin lacks a capability, the companion degrades exactly as for any provider without it; it never runs a provider's CLI, matches a provider id, or relaxes a rule for one provider.

## Logging

Allowed: opaque ids (`PullRequestKey` hash, `actionId`, `ActionRunId`, request ids). Forbidden: PR titles and bodies, comment, draft and guide text, remote URLs with credentials, tokens, one-time login codes, raw `gh` or `arc` output, `submitToken` params. Plugin errors are reduced to their typed code and reason before logging.

## Validation

`pnpm test:companion`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo fmt --all --check`. Recording fixture plugins prove the write triggers, stale head, idempotency and token absence in recorded companion ↔ plugin traffic; a companion test proves that no `companion/forge*`, `companion/pullRequest*` or `companion/review*` request is forwarded to App Server.
