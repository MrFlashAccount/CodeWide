# Agent provider layer

## Purpose and owner

`agent.rs` and `agent/**` are the companion's bounded context for talking to coding agents. All agent traffic — RPCs, events and runtime requests — reaches a provider only through the `AgentProvider` trait. Codex and Claude are equal adapters, each in its own crate. The cross-zone contract (neutral protocol, capability table, bindings, error codes, rollback) is in [`docs/agent-providers.md`](../../../../docs/agent-providers.md).

Code owner: backend. This document: architect.

## Crates

Dependency graph (an arrow points at a dependency):

```text
agent-transport        → agent-core
companion-host         → (redb, no agent crate)
agent-search           → (SQLite, no agent crate)
agent-resources        → agent-core, companion-host
agent-provider-codex   → agent-core, agent-transport, companion-host, agent-search, agent-resources
agent-provider-claude  → agent-core, companion-host, agent-search, agent-resources
companion-core         → all of the above
```

- [`crates/agent-core`](../../../agent-core/CONTEXT.md) — the neutral model, the `AgentProvider` contract, capabilities, provider-neutral token accounting and `wire-request-ids-v0`. Re-exported here as `agent::model` and `agent::provider`.
- `crates/agent-transport` — the JSON-RPC WebSocket and supervised stdio transports (`UpstreamHandle`), re-exported as `crate::upstream`.
- [`crates/companion-host`](../../../companion-host/CONTEXT.md) — narrow host contracts this crate implements for the adapters (thread index, canonical content, preview files, workspace VCS, derived index schemas, activity metrics).
- [`crates/agent-search`](../../../agent-search/CONTEXT.md) — the stored-message search index format and reads shared by the adapters.
- [`crates/agent-resources`](../../../agent-resources/CONTEXT.md) — the thread resource model, projection and reads shared by the adapters.
- [`crates/agent-provider-codex`](../../../agent-provider-codex/CONTEXT.md) — the Codex adapter and the Codex-owned storage.
- [`crates/agent-provider-claude`](../../../agent-provider-claude/CONTEXT.md) — the Claude adapter (Rust): drives the user's `claude` CLI over stream-json and reads and writes Claude's session store; it keeps an index of that store.

No adapter crate depends on `companion-core`; `companion-core` depends on both adapter crates only to wire them in.

## Module jobs

- `registry.rs` — enabled providers in configured order (primary first), the capability index, host-level capability owners (`host.fs`, `host.config`), the discovery providers, `is_multi_provider` (more than one provider enabled), the enabled providers' price tables (`usage_pricing`) and the parser of `agent-providers.json` with opaque per-provider entries. It names no concrete provider and does not import `providers/`; `build_registry` in `providers/mod.rs` is the only place outside the adapter crates that may name a provider id.
- `providers/mod.rs` — wiring of the adapter crates (`providers::codex`, `providers::claude` re-export them) and the configuration → adapter factory (`load_registry`, `build_registry`): the only code outside the adapter crates that maps a provider id to its adapter. `ProviderHost` hands the companion index, state directory, preview files and workspace VCS to adapters that keep their own index (Claude). Codex is always enabled; an invalid or unknown entry disables only that provider; a missing, unreadable or invalid file means Codex only; a configured primary without the merged (`codex.native`) surface is logged at `error` and Codex leads.
- `providers/codex_hub.rs` — Codex host integration of SyncHub: Codex-only registry constructors from an App Server connection (`SyncHub::new`, `SyncHub::with_mutations`) and installation of the Codex-owned account pool. Hosts with several providers use `build_registry`.
- `providers/codex_golden_tests.rs` with `providers/testdata/app_server_streams.jsonl` — golden replay of recorded App Server streams through the Codex adapter and the wire projector (byte-identical client wire).
- `bindings.rs` — the `agent_thread_bindings` store (record v2: segments), the `agent_thread_continuations` index, the `agent_bindings_backfill_v1` job (`run_backfill`), observation upserts, routing on a miss (`route`: bound, provisional or unknown) and `assemble_history` (an app thread's history from its segments).
- `client_wire/` — the single client-wire ↔ neutral translation: `decode.rs` (request classification), `gateway.rs` (routing by binding or capability, degradation errors, provisional-binding confirmation, `thread/start` provider choice), `items.rs` (a `command` item's `backgroundTaskId` becomes `codewideBackgroundTaskId`, omitted when absent), `results.rs` (also `companion/thread/backgroundTask/read`, gated by `threads.backgroundTaskOutput` in `decode.rs`), `events.rs`, `settings.rs`, `history.rs` (neutral → v0.155.1 projection), `request_ids` (`wire-request-ids-v0`, owned by `agent-core`), `list.rs` (merged `thread/list`), `catalog.rs` (merged `model/list` and `permissionProfile/list`). `mod.rs` owns `Thread.codewideAgent {provider, providerName, primary, capabilities}`; it and the `codewideAgentProvider` / `codewideAgentProviders` annotations are attached only in multi-provider mode.
- `permission_profiles.rs` — observes effective profiles from client-wire start/resume/fork results and settings events, and translates a profile inherited across providers into the target provider's catalog id; both orchestration spawn and cross-provider fork use it before creating a thread.
- `orchestration/` — the model-driven delegation context (one owner for every provider): `tools.rs` owns external DTO validation and the three task-addressed tools plus five compatibility facades; `admission.rs` freezes host provenance, permission ceiling and workspace policy; `task.rs` owns branded ids and the task/attempt/delivery state vocabulary; `journal.rs` owns durable coordination persistence, valid transition compare-and-set and task-local events; `coordinator/admission_plan.rs` owns pure admission planning and deterministic delegation identities; `coordinator.rs` owns the admitted task's runtime collaboration across workspace creation, child binding, turn delivery, recovery and cancellation; `delivery.rs` owns task-addressed blocking waits, authoritative result projection and the fallback-only `awaitingResume` acknowledgement path; `children.rs` keeps the durable parent → child compatibility projection; `lineage.rs` projects the existing client-wire child tree without leaking task state. `mod.rs` is the composition and live-observation boundary: it wires the service, routes authenticated calls and provider-tagged lifecycle facts, starts recovery and connects the compatibility tracker. `coordinator/watch.rs` owns only the in-memory current-turn/watch projection used by the five thread-addressed compatibility tools; it is not task or durable queue authority.
- `turn_delivery.rs` and `turn_delivery/pump.rs` — sole prompt-bearing command and durable command-state owner for reserved initial turns, user queue commands and agent follow-ups. They own reservation/promotion, stable command/client-message ids, queue mutation, provider dispatch, claims, receipts, retry scheduling, history reconciliation and retained receipts. `sync/queue.rs` is only the `companion/queue/*` DTO/RPC adapter over `TurnDelivery`; the pump resolves provider routes but keeps every durable transition behind the parent module's API. Atomic task admission enters through the transaction-scoped initial-turn reservation API exposed by `TurnDelivery`: it opens and commits the write transaction, writes the prompt-bearing reservation through its private storage helper, invokes the journal's prompt-free coordination writer in that same transaction, and rolls both sides back together. `TaskJournal` receives only the stable command id; it must not import a reservation DTO, `turn_delivery_tables` or any prompt-bearing table. Neither sync nor orchestration calls `IndexStore::outbox_*` or reservation-table helpers directly. `IndexStore` and `store/turn_delivery_tables.rs` own atomic storage primitives/schema only, not queue or delivery policy. The journal and orchestration tables must not contain command params or another prompt copy.
- `fork/` — fork into another provider: `mod.rs` (`ForkService`: create, durable fork record, inherited-title materialization of an otherwise empty target, pending handoff injected into the first `turn/start`), `handoff.rs` (pure history selection and budgeting, ported from t3code).
- Direct input: `items.rs` sets `Thread.canAcceptDirectInput` from the neutral status (`false` for `openElsewhere`, otherwise `true`: a neutral provider reports a held thread as `openElsewhere`, so an unloaded one is free), and `events.rs` repeats it on every `thread/status/changed` of a neutral thread so the client applies a lock and its release live, including the release to `notLoaded`; Codex App Server status changes omit it. A queued turn waits on an `openElsewhere` thread (`ThreadActivity::Unavailable`).
- `client_wire/observe.rs` — the facts read back from client-wire payloads (turn lifecycle, effective permission profile).
- `provider_status.rs` — `companion/agentProviders/read` (every configured provider with status, sign-in state and capabilities, plus host capabilities) and the durable `companion/agentProviders/changed` notifier (multi-provider mode only), built from `AgentProvider::status`/`health`/`subscribe_rate_limits` (optional `accountLabel` and `rateLimits` entry fields, omitted when not applicable); it names no provider.
- `testing.rs` — the in-memory fake providers for unit tests of this layer (`FakeProvider`, `ScriptedProvider`).

SyncHub (`sync.rs` and `sync/`) keeps sessions, queue RPC adaptation and ingest; durable command dispatch and state policy stay inside `turn_delivery`. `companion/search*` goes to the `history.messageSearch` owner with the `codex.native` surface; when an enabled provider searches its own stored history (`AgentProvider::message_search`, Claude), its threads' reads go to it and a global `companion/search` merges every searching provider's hits (`sync/search_routing.rs`); a Codex-only host keeps the single-owner path. Thread resources work the same way: a provider with its own resources (`AgentProvider::thread_resources`, Claude) answers its threads' resource reads and prewarms and observes its own events (`ResourceRoute` in ingest); every other thread keeps the `history.threadResources` owner. It holds the `ProviderRegistry`, routes RPCs through `client_wire`, starts the provider-delivery pump owned by `turn_delivery`, spawns the backfill job for each discovery provider (active mutation mode only, 30 s after startup), and runs one ordered forwarder per provider into the existing ingest channel. A provider `busy` result is resolved by `TurnDelivery` as the durable wait-until-idle transition. SyncHub no longer holds a raw `UpstreamHandle`. It reaches thread history, message search and thread resources only through the `NativeSurface` storage traits of the capability owner (or of the thread's own provider), never by provider id. Ingest projects live usage with `crate::usage::LiveUsageProjector`, priced by the thread's own provider's table (`UsagePricing::for_provider`; the provider is recorded per thread from its forwarder's `IngestInput::ProviderPayload`) or by the provider-reported cost (`codewideProviderCost`); pricing inputs, never prices, are journaled (`agent_core::usage::prepare_replay_payload`). Pins are companion state in `thread_pins.rs` and the store, not agent storage.

Delivery projects every journaled event through `sync/replay.rs`, for initial catch-up, snapshot catch-up and live delivery. Its `ReplayProjector` reads the thread's durable binding and selects only that provider's `usage_pricing`; an unbound event may use the primary's rates only on a single-provider host. A missing or disabled provider table leaves the estimate unavailable. Provider-reported costs survive without a table. The native thread store adds catalog metadata after pricing and must preserve usage costs.

The host side of the adapters' storage stays here: `store.rs` (`IndexStore`) owns the index database, its schema version and the companion tables, migrates registered derived schemas (`IndexStore::open_with`) and implements `HostThreadIndex`; `content.rs` asks a `CanonicalContentSource` before its own bytes; `server/services.rs` resolves unknown threads through a `ThreadMetadataSource`; `files.rs` and `vcs.rs` implement `PreviewFiles` and `WorkspaceVcs`. `user_message_projection.rs` projects user messages for display before content projection on every lane (ingest, RPC results): it picks the thread's provider cleaner (`ProviderRegistry::user_text_cleaners`, the primary's for an unknown thread), removes only the companion's own formats itself, and drops a message or notification left with nothing the user wrote.

## Binding segments

- A binding is an ordered list of segments `{provider, nativeThreadId, firstTurnOrdinal, lastTurnOrdinal | null, handoffRefs[]}`. The app thread id is the first segment's native id; routing uses the active (last) segment.
- Record v2 keeps the v1 fields (`activeProvider`, `refs`) as a projection, so an older companion still routes it. v1 records are upgraded once on open (marker `agent_bindings_segments_v2` in `agent_meta`) and read as one segment until then.
- A native thread that is a non-first segment (a continuation, indexed in `agent_thread_continuations`) is never its own app thread: merged `thread/list` rows and global search hits of it are dropped, binding observation and backfill skip it, and a call addressed to it is `thread not found`.
- An app thread's history is its segments' native turns in segment order, a closed segment contributing at most its ordinal span (`assemble_history`).
- Every neutral turn and item carries optional `provenance {provider, nativeThreadId}`; the adapters stamp it, the client wire never shows it.
- Exactly one segment is written per binding. Switching providers inside a thread is dropped (owner decision); fork into another agent and cross-provider subagents replace it.

## Invariants

- The binding decides the provider. Model id, `thread_metadata.model_provider` and id shape never do. Every thread has an explicit binding; an upsert never changes an existing binding's provider.
- Discovery on a miss: with exactly one `threads.externalDiscovery` provider the call is routed provisionally to it (no `thread.owns` call) and the `discovered` binding is written only after that provider accepts the call; with several, `thread.owns` is asked in registry order and the first owner is bound before routing; otherwise `-32600 "thread not found: <id>"`.
- A host with one enabled provider emits no client-wire extension field; its wire is byte-for-byte today's.
- Capabilities decide features and degradation. A thread-scoped call without the mapped capability returns `-32072` without contacting the provider.
- The neutral → wire translation exists once, in `client_wire`. Adapters never emit client-wire JSON.
- Neutral `turn.start` never steers; steer is only explicit `turn.steer`.
- Phase-1 binding: exactly one segment, its native id equal to `appThreadId`; the provider never changes.
- One accepted delegation creates one durable task, one authoritative first attempt and one dedicated child thread. Follow-up child turns never change the task's terminal result.
- `TaskState` and `DeliveryState` are separate discriminated unions with separate compare-and-set transitions. The first terminal task state wins; delivery may acknowledge or defer that result but cannot reopen, fail or cancel the task.
- A pre-admission rejection creates no task. Every post-admission uncertain start is addressable by stable `taskId` and `attemptId`; no automatic retry creates another child or authoritative turn.
- `wait_task` and `cancel_task` resolve the immutable task → authoritative attempt → provider turn chain. `wait_agent`, `send_agent` and `cancel_agent` remain thread/current-turn operations and cannot acknowledge or rewrite a task.
- The orchestration journal stores coordination metadata and stable command references only. Prompt-bearing reservations and outbox commands belong exclusively to `turn_delivery`; transcript, final answer, account label, URL, credentials and arbitrary provider payload remain in their existing owners.
- Provenance and the parent permission ceiling come from authenticated host context and are immutable for a task. Model arguments may only request a narrower profile and one of `sharedReadOnly` or `isolatedWrite`; shared write is not agent-selectable.
- The `codewide_spawn_agent` compatibility decoder keeps its legacy arguments, required result fields and errors, but the host converts the decoded call before durable admission. Missing `permissionProfile` or explicit `:read-only` maps to `sharedReadOnly` at the requested absolute `cwd` or the authenticated parent's cwd. An explicit write-capable profile maps to `isolatedWrite`, using that path only as `sourceWorkspace`, and still passes the parent-ceiling and provider-translation checks. The compatibility path never newly admits `LegacyShared`, never inherits a writable shared profile, and never treats model-supplied `cwd` as shared-write authority. A future shared-write compatibility path requires a host-minted grant from a separate user-owned surface, bound to the authenticated parent and approved cwd/permission ceiling; the model-facing legacy DTO cannot carry or mint that grant, and no such path exists in this slice.
- Provider differences enter orchestration only through neutral capabilities and adapter-local ports. Common orchestration code never branches on provider id.

## Dependency rules (`must_not_import`, checked by grep in review)

- `agent-core`, `agent-transport`, `companion-host` and the adapter crates must not depend on `companion-core`; the adapter crates must not depend on each other.
- `client_wire`, `registry` and `bindings` must not import `agent::providers`, `agent_provider_codex`, `agent_provider_claude` or `upstream`.
- `sync.rs` must not import `upstream` request APIs.
- `sync.rs`, `sync/*`, `thread_view.rs` and `sync_pending.rs` must not import `agent_provider_codex`; they reach Codex storage only through the `NativeSurface` storage traits of the capability owner.
- The queued-steer path in `sync.rs`, `sync/queue.rs` and orchestration may depend on `turn_delivery`; they must not call `IndexStore::outbox_*`, import `turn_delivery_tables`, accept its reservation DTOs or reproduce queue-state transitions. Atomic admission crosses one transaction-scoped `TurnDelivery` API: `turn_delivery` owns the prompt-bearing reservation and transaction lifecycle, while the journal contributes only prompt-free coordination writes through the callback/transaction capability supplied by that API. `IndexStore` and the private reservation-table helper must not choose queue or delivery policy.
- No `match`/`if` on a `ProviderId` value outside the adapter crates and the factory in `providers/mod.rs`.
- Only `providers/`, `managed_runtime.rs` (the composition root) and test code import `agent_provider_codex`; this crate names no rollout format, `state_5.sqlite` path or `OpenAI` price outside that wiring.
- `orchestration` must not import provider adapters, App Server `toolOutput` shapes, Claude MCP frames or Android/client-wire DTOs. `orchestration.externalDelivery` is reserved protocol vocabulary only in this slice; both adapters advertise false and no provider-native completion port is wired.
- Android and client-wire projections must not import or decode orchestration task, attempt, event, permission-envelope, workspace-claim or delivery storage records.
- The journal must not dispatch provider calls or own or import a prompt-bearing reservation, turn-command payload, claim, receipt or retry state; those belong to `turn_delivery` and provider adapters. Negative source checks must prove `journal.rs` and the orchestration context do not depend on prompt-bearing reservation DTOs (including `ReservedTurnCommand` or `InitialTurnReservation`), `turn_delivery_tables` or reservation-table constants/helpers; a persistence test must decode orchestration records and prove command params and prompt text are absent.

## Compatibility surfaces

- **`codex.native`** and **`wire-request-ids-v0`** (`keep_temporarily`, backend) — defined in [`docs/agent-providers.md`](../../../../docs/agent-providers.md#compatibility-surfaces) with their removal conditions and negative checks.
- **Five thread-addressed orchestration tools** (`keep_temporarily`, backend) — `codewide_spawn_agent`, `codewide_wait_agent`, `codewide_send_agent`, `codewide_cancel_agent` and `codewide_list_agents` keep their existing inputs, mandatory result fields and errors until persisted Codex specs and supported Claude sessions stop using them for one release window. They are facades, not aliases for task acknowledgement/cancellation.
- **Legacy spawn workspace mapping** (`keep_temporarily`, backend) — `codewide_spawn_agent` preserves its public DTO and result, then maps an omitted or read-only profile to `sharedReadOnly` and an explicit write-capable profile to `isolatedWrite`. `LegacyShared` is not newly admissible. Shared write requires a separate host-owned, user-granted capability bound to the authenticated call context; absent that grant, the model-facing compatibility tool cannot select shared write or widen cwd authority.
- **Child-link v1** (`public_exception`, backend read owner) — legacy parent/child records remain readable forever and are never backfilled with synthetic task, attempt, phase, cost or provenance data.

## Orchestration tools and fork

- The tool semantics live only in `orchestration/`; adapters translate declarations and calls to their channel (`ClientToolHost`). A call is accepted only for a thread bound to the provider whose authenticated channel carried it, and addresses only that thread's children or tasks.
- `codewide_delegate_task` admits one durable task with `blocking` or `deferred` wait mode. `codewide_wait_task` and `codewide_cancel_task` address that task, not the child's current turn. The five existing agent tools retain thread-addressed compatibility semantics.
- `sharedReadOnly` forces read-only. `isolatedWrite` obtains its directory only through `workspace.create@1` and fails closed when unavailable; a retained workspace is not reset, cleaned or deleted by this context.
- `codewide_spawn_agent` keeps its legacy argument/result surface but uses the safe mapping above. Omitting `permissionProfile` selects shared read-only; only an explicit write-capable profile selects isolation. Its optional `cwd` is a read-only cwd or isolated source, never a shared-write grant.
- Spawned agents never exceed the caller's frozen permission ceiling; an unknown caller profile allows only `:read-only`. Arguments claiming user provenance, shared-write authority or a permission ceiling are rejected as unknown external fields.
- Blocking waits are event-driven (no polling) and end with their timeout or the calling turn. Ending the caller turn does not cancel accepted child work.
- Initial and queued follow-up prompts go through `turn_delivery`; orchestration retains only stable command references. A provider-minted start with uncertain acknowledgement enters durable start reconciliation and is never retried automatically.
- `delegateTaskEnabled` is a host-owned pre-admission gate. It may stop new `codewide_delegate_task` writes without disabling `wait_task`, `cancel_task` or the five compatibility tools needed to recover existing work.
- Completion delivery is fallback-only: `Pending → AwaitingResume → Acknowledged`. Both adapters advertise `orchestration.externalDelivery: false`; there is no native completion switch, reservation or reconciliation machine until a future approved slice supplies source, tests and pinned-provider probe evidence.
- A fork to another provider never changes the source thread; its handoff waits durably for the first turn. While it waits, the inherited title makes an empty Codex target resumable without starting a synthetic turn.
- Neither service branches on a provider id.
