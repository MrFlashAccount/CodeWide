# V1 connections

TypeScript/TSX owns pairing sessions, profile-edit admission and server presentation. Wire validation, credential storage, startup and reconnect remain in data/native authorities. M1 implementation is present; device scanning and settings smoke have not run on this host.

Public surfaces are `ConnectionSheet`, `connectionSettingsSections` in `ConnectionFeature`, `useConnectionActions`, `useHostUpdateProjection`, the corresponding narrow input contracts, and connection/server presentation exports. Workspace binds existing methods without passing RemoteWorkspace. Settings consumes the public settings-record factory and host-update projection; list/navigation may consume server projection and display types. Private pairing modes, row forms and state hooks are not cross-feature APIs.

`hostUpdateResource` is the process-lifetime owner for authenticated `/v1/host-update` status, check, apply, operation and reconnect calls. It retains one client idempotency key and exact signed target fingerprint through the expected Companion disconnect, retries a lost `202` with the same intent, and reconciles the durable operation after the same device reconnects. A legacy authenticated `404` is the unsupported/manual path, not a connection failure. Settings demand rereads status once the latest read, successful or failed, is 30 seconds old, so a Companion or Relay restart that no settings surface observed cannot leave a stale version; a failed read is not repeated on every render. Settings never imports its transport, session authority or private model; it renders only the public per-connection projection and emits check/apply intents. One request runs per connection: a check requested during a background read runs right after it, and an apply registered meanwhile is sent right after it. Until the server answers, the view carries `pending` (`apply` or `check`); the card keeps the confirmed text, shimmers the version and keeps its action in place, disabled and busy. It never claims `accepted` before the 202, and a concurrent status read cannot offer Update again for an unsent intent. `hostUpdateOperationFollower` owns the request sequence of one reconcile pass; the resource owns scheduling, failures and fencing.

Update HTTP demand depends on the saved connection being enabled, independently of WebSocket/App Server health. The transport bounds origin/session resolution, HTTP and body reading together and fences late sends after timeout. Terminal errors survive a status refresh that omits a completed operation. Optional guardian progress is validated at the wire adapter and shows download bytes/percent and the confirmed install stage. The connection row prioritizes that active update over expected reconnect errors. During an HTTP interruption it labels the observation as last confirmed and waits for fresh status; it never presents cached progress as current server reachability. While an operation is active, every non-rejecting failure (no answer, `HostUpdateUnreachableError` timeouts, 502/503/504) keeps the last confirmed stage and retries; only a terminal phase or a definitive HTTP rejection ends it. A background read without an operation that cannot reach a server whose status was already confirmed (for example the Relay card while Companion restarts) keeps that status as last confirmed and retries for 60 seconds before showing the failure; a user-requested check shows its failure at once. Progress text is platform-neutral: macOS and Linux render the same stages.

One mounted pairing session retains form contents through close and resets on the next open identity. Its save checks local readiness before consuming pairing, preserves the 650 ms success display, and keeps lower credential validation unchanged. `connectionActions` distinguishes profile-only edits from credential/runtime updates and emits successful-add intent to navigation. The row editor retains unsaved values, failures and diagnostic expansion at the same mounted lifetime.

Local styles follow pairing/editor/status owners. Only explicit account public surfaces are consumed here. No V2 import, lower-to-feature edge, feature-owned runtime/cache, private cross-feature import or root-composition dependency is allowed.

Verification: `host-update-resource.test.ts`, `v1-host-update-settings.render.test.tsx`, `v1-pairing-session.render.test.tsx`, `v1-settings-feature-contract.test.ts`, pairing/connection semantic tests, native configuration and transport-security contracts, and `pnpm validate:android:v1`. Camera scanning requires a device; no device was attached in the M1 check.

M7 capability closure: `workspaceCapabilities.ts` exposes only this owner's qualified operations. Private `workspaceAdapter.ts` binds existing lower model/session authority through exact workspace composition; it does not own shared in-flight maps, runtime construction or global cleanup. The broad RemoteWorkspace facade is deleted.

Agent provider status: the server detail page reads the model-owned provider list (`data/agentProvidersResource.ts`, `companion/agentProviders/read` on the detail-page open intent, `companion/agentProviders/changed` from the journal) and `AgentProviderMarks` shows each provider as a mark beside the connection switch, tinted when it needs attention, with its status and sign-in (`agentProviderPresentation.ts`) as the accessibility label, only when the server lists more than one provider. Providers are never shown as pool accounts; an older Companion (`-32601`) shows nothing new. A provider without an account pool (Claude) additionally gets its read-only account section from the accounts owner (`ProviderAccounts`). Marks come from `ui/ProviderIcon` ( `ui/providerBrand.ts` is the only provider-id → mark/product-name mapping, with a generic mark for unknown ids; the Claude and OpenAI marks are third-party trademarks used only to identify the provider).

Server refresh: the server detail page's header carries one refresh (`ServerRefreshButton`, passed as the settings record's `headerAction`). It reruns every read the page shows — the account pool, the provider list (sign-ins and limits), and the Companion and Relay update checks — together; each result and error stays with its owner, and the button only shows that they run. The account pool section has no refresh of its own.
