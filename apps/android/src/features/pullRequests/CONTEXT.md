# V1 pull requests catalog

Public surfaces: `PullRequestsFeature` (`PullRequestsCatalog`, the `/pulls` content for one connection), `CatalogModeBar` (the Threads | Pull requests switcher), `PullRequestsHeader` and `pullRequestListModel` (the applied search plus atomic filter-tray draft and the Accounts sheet switch). `/pulls` is a top-level workspace destination, not a scene inside the Threads list stack: its header and content commit together, and the retained Threads header, search, rows and New message action are hidden for the whole route. `WorkspacePaneLayout` is the only owner and caller of `WorkspaceTwoPaneLayout`: on a wide viewport it keeps the Pull requests catalog mounted in the bounded left column while a selected PR opens in the rounded right detail surface; compact viewports show only the focused catalog or detail. Pull-request route components project catalog or preview content into those slots and must not create a nested split layout. The layered review illustration belongs only to the no-linked-account onboarding state; once an account is linked, the empty wide destination uses `PullRequestSelectionPlaceholder`, parallel to the chat selection placeholder. `WorkspacePaneLayout` also owns one persistent floating `CatalogModeBarHost` across both root destinations. Its vendored Reacticx Masked Tab Bar starts pointer-driven selection motion in the gesture worklet before route rendering reaches the JavaScript thread, then reconciles the controlled value without remounting. A separate invisible overlay provides native tab semantics without modifying the visual component. `workspaceCapabilities.ts` declares the connect and account mutations; the private `workspaceAdapter.ts` binds them through `createWorkspaceFeatures` only.

The feature owns presentation and interaction policy of the catalog: a welcome surface with one connect action; the server-declared provider list and nested connect views inside the unchanged vendored Reacticx Tray; connect methods (`linkExisting`, `hostLogin` with the one-time code and one open-link button, `pasteToken`, `instructions` with Check again); the optional checks credential; account states (`connected`, `expired`, `error`); disconnect modes (`unlink` by default, `forgetToken` for saved tokens, `logoutHost` only behind a destructive dialog); the PR list with problem rows plus global `Need attention` and `Up to date` groups; the shared catalog search trigger and pull gesture, an independent sort menu and a responsive filter tray; and the offline snapshot notice. The catalog always starts from the provider-neutral `All` category and renders no chip row below search. The tray edits only structured filters in an isolated draft: outside dismissal discards it, `Reset` clears only those structured conditions and is disabled when none are active, and `Apply` publishes the whole query once. Search text and sort remain independent from the tray. Values inside a field are ORed, fields are ANDed, and provider-specific conditions must be rejected rather than silently ignored. Rows keep a fixed provider slot and show a dot only for an undisplayed Companion-issued attention revision. Opening a PR hides that dot through the shared process projection without moving the row; the next authoritative list read applies the durable group change. A query with no rows fills the remaining catalog with a calm zero-inbox state; searches or explicit filters use distinct no-match copy rather than claiming the inbox is clear. Filter changes retain the published list through a Transition/deferred query and shimmer the changed control until the next keyed snapshot replaces it. Onboarding always keeps four explicit views: provider, method, authentication and terminal success. It opens the provider list first even when only one provider is available, and the catalog keeps that journey mounted while its Tray is open so a live account refresh cannot replace the success view with the PR list. Its Tray header is one row: the left group is `Back? → Title → Step`, while `Close` is the only right-side control.

Data and Promise identity stay in the process-owned TanStack `QueryClient` in `data/forgeResources.ts`; this feature reads Query resources during render and never mirrors them. Persisted list and recent-overview snapshots hydrate stale entries before live revalidation. Replay-safe PR and review writes persist their exact allowlisted envelopes through `data/forgeMutationQueue.ts`; auth and token operations never enter that journal. Pending connect state lives in `onboarding/onboardingModel.ts`; a live host-login flow is companion-owned and re-read from the accounts resource, so it survives app restarts.

Tokens: a pasted token lives only in `TokenPasteSheet` component state, is cleared on submit, dismiss and error, and is sent once by `submitToken` directly on the session (no outbox, no request telemetry). Provider-supplied URLs open only when `https` on the provider host (`onboarding/providerUrl.ts`).

Boundaries: this feature must not import `features/pullRequestDetail` (and the reverse); they meet only through `routeComposition` navigation intents. `features/threadList` must not import this feature. Behavior branches on capabilities and descriptor kinds, never on plugin ids or forge names.
