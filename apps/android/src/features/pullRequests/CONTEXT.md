# V1 pull requests catalog

Public surfaces: `PullRequestsFeature` (`PullRequestsCatalog`, the complete `/pulls` catalog chrome and content for one connection), `CatalogModeBar` (the visual Threads | Pull requests control), `PullRequestsHeader` and `pullRequestListModel` (the applied search plus atomic filter-tray draft and the Accounts sheet switch). `/pulls` is the real catalog route anchored by the URL-invisible `(tabs)/(pull-requests)` Stack, not a scene inside Threads and not a catalog constructed by route composition. `PullRequestsWorkspaceRouteLayout` renders that route descriptor exactly once and supplies it with the selected PR slot to `WorkspaceTwoPaneLayout`; compact viewports show only the focused catalog or detail, while wide viewports keep the real catalog in the bounded left column. Pull-request route components provide route-owned content and must not create a nested split layout. The connected catalog mounts its header and list inside the shared `CatalogSearchOverlayHost`, so search covers their complete bounds exactly as it does for Threads. The layered review illustration belongs only to the no-linked-account onboarding state; once an account is linked, the empty wide destination uses `PullRequestSelectionPlaceholder`, parallel to the chat selection placeholder. The parent `WorkspaceTabsRouteLayout` owns the one `CatalogModeBarHost`, exact route-name mapping and TabRouter actions. `CatalogModeBar` owns geometry and visual interaction only; it exposes distinct selected activation so the parent can emit cancelable `tabPress` for reselect without changing `onValueChange`. Switching tabs retains this Stack, its PR route key and the canonical Details or Changes URL. The feature owns neither Router history nor the active-tab record. Its vendored Reacticx Masked Tab Bar starts pointer-driven selection motion in the gesture worklet before route rendering reaches the JavaScript thread, then reconciles the controlled value without remounting. The vendored Reacticx source is authoritative, generated `masked-tab-bar.js` is output-only, and `masked-tab-bar.d.ts` is maintained separately. `workspaceCapabilities.ts` declares the connect and account mutations; the private `workspaceAdapter.ts` binds them through `createWorkspaceFeatures` only.

The feature owns presentation and interaction policy of the catalog: a welcome surface with one connect action; the server-declared provider list and nested connect views inside the unchanged vendored Reacticx Tray; connect methods (`linkExisting`, `hostLogin` with the one-time code and one open-link button, `pasteToken`, `instructions` with Check again); the optional checks credential; account states (`connected`, `expired`, `error`); the Accounts sheet behind the catalog `+`, shaped like the account pool: one group per registered provider with its linked accounts and one `Add <forge> account` row that opens that provider's sign-in in its own `AppSheet` (`onboarding/ProviderSignInSheet`, sharing `useProviderJourney` with the Tray); each account row carries the `companion/forge/account/setEnabled` catalog switch (requested value and shimmering login while pending, authoritative value and the reason on failure) and an overflow menu with Check again and the removal modes (`unlink` by default, `forgetToken` for saved tokens, `logoutHost` only behind a destructive dialog); providers have no on/off anywhere in the app — a provider disabled in the Companion registry is listed like any other with its accounts and Add account, and a provider whose plugin is `missing` or `failed` shows that state with the Companion's reason and no Add account; an account excluded from the catalog is hidden everywhere in the catalog UI, including the filter tray's account sources, while branch detection and PR–thread linking keep using it; opening the sheet or the onboarding Tray revalidates the accounts query in place; the PR list with problem rows plus global `Need attention` and `Up to date` groups; the shared catalog search trigger and pull gesture, an independent sort menu and a responsive filter tray; and the offline snapshot notice. The catalog always starts from the provider-neutral `Involved` category: only pull requests involving the connected account are eligible, while `All` is an explicit non-default scope. It renders no chip row below search. The tray edits only structured filters in an isolated draft: outside dismissal discards it, `Reset` appears only when the draft contains a structured condition and clears only those conditions, and `Apply` publishes the whole query once. On every viewport the facet index and facet editor are separate Reacticx `Tray.View` entries so forward and back navigation use the Tray's native-thread transition. The filter surface is capped to the visual viewport above the IME and cancels the duplicated navigation-bar inset while the keyboard is open. Search text and sort remain independent from the tray. Values inside a field are ORed, fields are ANDed, and provider-specific conditions must be rejected rather than silently ignored. Rows render through the shared `ui/CatalogRow` parts and `catalogRowFrameStyles`, the same frame, typography and trailing meta as Threads rows; this feature supplies only content. Rows keep a fixed provider slot in the title line and show the catalog unread marker only for an undisplayed Companion-issued attention revision. Opening a PR hides that dot through the shared process projection without moving the row; the next authoritative list read applies the durable group change. Independently, a row whose Companion-listed canonical review chat (`reviewThreadId`) is unread in the thread catalog shows the `agentReply` marker (a chat glyph in the unread colour) before that dot; both may show at once. Unread state comes only from the thread catalog's `ProjectUnreadModel` through the route-supplied `isThreadUnread` reader, read inside the row's selector; this feature keeps no copy of it, and reading the chat clears the marker. A query with no rows fills the remaining catalog with a calm zero-inbox state; searches or explicit filters use distinct no-match copy rather than claiming the inbox is clear. Filter changes and stale-while-revalidate refreshes keep the published list in place and show one loader directly to the right of the `Pull requests` title until the next keyed snapshot arrives; refresh status never inserts or removes list geometry. Onboarding always keeps four explicit views: provider, method, authentication and terminal success. It opens the provider list first even when only one provider is available, and the catalog keeps that journey mounted while its Tray is open so a live account refresh cannot replace the success view with the PR list. Its Tray header is one row: the left group is `Back? → Title → Step`, while `Close` is the only right-side control.

Data and Promise identity stay in the process-owned TanStack `QueryClient` in `data/forgeResources.ts`; this feature reads Query resources during render and never mirrors them. Persisted list and recent-overview snapshots hydrate stale entries before live revalidation. Replay-safe PR and review writes persist their exact allowlisted envelopes through `data/forgeMutationQueue.ts`; auth and token operations never enter that journal. Pending connect state lives in `onboarding/onboardingModel.ts`; a live host-login flow is companion-owned and re-read from the accounts resource, so it survives app restarts.

Tokens: a pasted token lives only in `TrayTokenPanel` component state, is cleared on submit, dismiss and error, and is sent once by `submitToken` directly on the session (no outbox, no request telemetry). Provider-supplied URLs open only when `https` on the provider host (`onboarding/providerUrl.ts`).

Boundaries: this feature must not import `features/pullRequestDetail` (and the reverse); they meet only through typed `routeComposition` navigation intents. It must not import Expo Router, route files, either child route-layout owner, the parent `(tabs)` layout or `WorkspaceTwoPaneLayout`. `features/threadList` must not import this feature. Route composition may import the feature's public surfaces, but the feature does not own the `/pulls` descriptor, selected PR, selected tab, Back history, inactive-scene isolation or pane geometry. Details and Changes remain canonical sibling URLs and must not be mirrored in the feature model. Behavior branches on capabilities and descriptor kinds, never on plugin ids or forge names.
