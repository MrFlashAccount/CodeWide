# V1 review

Public surfaces: ReviewFeature binds the mounted review session; comments/LineCommentFrame docks the one line comment composer (comments/LineCommentComposer) under review content, with comments/lineCommentDrafts (its per-line text owner); comments/DraftCard (saved drafts and `DraftPutCard` for new drafts not saved yet) presents companion-owned drafts with their per-axis badges; guide/GuidePanel walks an agent-written guide over a caller-owned diff source; reviewTargetCapabilities (bound by reviewTargetAdapter) mutate drafts and guides; workspace/CodeReviewWorkspace presents the current thread's own file changes without a guide entry; ReviewTargetSheet chooses the existing review command; comments/reviewSubmission prepares text attachments; resources/reviewFiles converts received change resources. Resource loading, line comments, voice binding and view settings have private owners.

The feature owns the complete code review editor. `editor/` contains the native and web adapters (one props contract, `editor/codeReviewEditorProps.ts`), typed bridge and display policy. `editor/webview/` is the browser-only Pierre application and its authored HTML template; `sync-code-review-editor-asset.mjs` bundles that entry into Android assets. The browser entry uses a `.web.ts` suffix so the web TypeScript graph checks its DOM contract while the native graph excludes it. Generated Android assets are outputs, not source owners. The WebView only displays: the document, the tree, inline comments (`saved`, `pending` with its text under a CSS text shimmer, `failed` with the owner's reason) and the anchor line the host sends as `selection`. It reports line taps and never hosts a composer; there is no draft, voice or submit message on the bridge.

Line composer: a line tap, in the PR Changes tab and in the current-thread review workspace alike, opens exactly one `LineCommentComposer` docked at the bottom of the review content by `LineCommentFrame`, like a chat reply: no sheet, modal window or scrim, so the diff above keeps scrolling, text selection and line taps, and the content keeps the collapsed composer's height clear. `ui/KeyboardDock` keeps it above the keyboard by resizing its layer (Keyboard Controller's `KeyboardAvoidingView` measured in the window; inside a fullscreen modal, the Compose dialog's IME insets). The composer is an anchor row (`file · line N`, the full path in its accessibility label, Expand and Close) over the chat composer's input row: the public Markdown input and one trailing round action, the chat microphone (`ComposerMicrophone`, with the recording meter in place of the editor while dictating, over the retained VoiceInputController through `comments/lineCommentVoice.ts`; no second recording runtime) while there is nothing to send or a dictation is running, else the chat's arrow-up send (`ComposerSendButton`) labelled by the owner. There is no title, destination picker or separate button. The anchored line stays highlighted while it is open. Tapping another line re-anchors the same composer and its typed text (`lineCommentDrafts.move`; a text the other line already held moves to the line left behind). Expand fills the frame above the keyboard with the same editor as a document: the anchor row, a one-line monospace quote of the commented line (green bar for the new side, red for the old, square left edge; hidden when the tap carried no line text), the borderless editor drawn from the top-left, and a bottom bar with the microphone and the owner's label as a text submit, disabled while empty. The quote comes from the tap: the WebView fills `CodeReviewLineReference.context` from the document it was tapped in (`editor/webview/lineText.web.ts`: the file source, the before/after file of a diff, or the recorded patch hunk) and `LineCommentTarget.context` carries it; it is not part of the line's draft identity. It switches without a layout transition (so there is no motion for Reduce Motion to still): the dock moves with the keyboard every frame, and a layout transition on the composer would trail it. Close, Back and Send close it. Send never waits for a write: the composer closes at once and hands the line and text to its owner, so it has no busy state. Unsent text lives per line in `lineCommentDrafts` and outlives the composer; a voice binding captures its line, so a transcript that arrives after the composer closed or was re-anchored lands on the line it started on (the voice scope is the review window plus the line). The chat composer has no hardware-keyboard send shortcut, so neither does this one.

Source publishes before diff completion. Abort checks guard publication and final materialization; existing async-resource keys and revision identities remain authoritative. Composer owns draft attachment admission and identity-checked acknowledgement through its reviewAdmission capability. The shared `rendering/ContentReviewHost` remains outside this feature because Markdown, image, diagram and attachment renderers use its cross-renderer selection and session lifetime. The feature does not own those generic annotation primitives.

M4 review: V1 gate passed (2189 modules, 7677 dependencies), 83 focused semantic/source/boundary checks and two render checks passed. Tests preserve delayed line transcript, selected-line isolation and acknowledgement of only the sent attachment. Actual Android voice/WebView interaction remains unverified under the resolved device disclosure.

M7 capability closure: `workspaceCapabilities.ts` exposes only this owner's qualified operations. Private `workspaceAdapter.ts` binds existing lower model/session authority through exact workspace composition; it does not own shared in-flight maps, runtime construction or global cleanup. The broad RemoteWorkspace facade is deleted.

Pull-request review: this feature is forge-independent and must not import `features/pullRequest*`; the PR screen depends on it and owns its separate Files / Guide surface. Drafts and guides are companion-owned (`data/reviewResources.ts`); PR drafts reach a forge only through Submit review on the PR screen. The line composer has no destination choice: on a PR source a new line comment is always a `pr` draft, and the current-thread workspace's comments are local agent review comments. Existing Agent and Both drafts keep their badges and Send to agent on their cards. A new draft's `putDraft` is the persisted durable write; until the drafts snapshot holds it, `data/reviewDraftPuts.ts` lists it from the shared MutationCache (saving, or refused with the Companion's reason), so callers show it at once without awaiting. On acknowledgement the adapter patches the saved draft into the drafts query and forgets the write in the same task, then re-reads; a refused new draft stays listed until `dismissDraftPut` (restore or discard), a refused re-anchor is dropped. Session and VCS line comments keep the existing local list and composer review admission, but the current-thread Changes workspace never exposes the pull-request guide. Guide prose is untrusted agent output, rendered as plain text and labelled with its author thread.
