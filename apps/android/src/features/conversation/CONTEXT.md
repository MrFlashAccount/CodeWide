# V1 conversation ownership

M6–M8 source extraction is implemented. The temporary command aggregation and lower facade are deleted. ConversationWorkspace receives owner-qualified capabilities and explicit model reads; private scope binding and render factories preserve the original mounted hierarchy.

ConversationWorkspace composes public feature capabilities. ConversationDetail owns model reads and progressive restoration; it publishes its snapshot through a render slot. ConversationReadSurface composes only read capabilities, timeline and read-only slots for subagents. ConversationComposition assembles the main editor and tools through their public owner entrypoints. A thread whose `canAcceptDirectInput` is `false` renders read-only (`data/threadDirectInput.ts`): a sub-agent, which its parent agent drives, or a thread another app holds (open elsewhere: refuses input and has no `parentThreadId`). Only an open-elsewhere thread shows the persistent `ui/ThreadOpenElsewhereNotice` bar in the editor's place under the read-only composer chips, instead of a matching send failure: "Open in another app" (pressing it opens a details popover: what the lock means and what both actions do), a Fork button that opens the fork sheet for the whole chat, and the primary Check again, which re-reads the thread authoritatively (`surface.recheckThread`; the label shimmers while it runs). Its header keeps the thread menu with only Compact context and Delete thread off. A sub-agent keeps the same menu: `threadHeaderActions` classifies every action as reading or mutating the thread, so Copy session ID and Fork stay enabled while Rename, Pin, Compact, Archive and Delete show disabled with "Read-only thread". A new chat has no menu. A host may present the conversation as a `pane` (`ConversationHostPresentation`): no back arrow, a trailing close, and the host's pane actions listed first in the same single thread menu; the default `screen` presentation is the ordinary thread header. A conversation placed on the recessed workspace frame (`ui/surfaceTone`) paints its canvas in the frame color and raises its message bubbles to the destination color. The live `thread/status/changed` patch, or a check that finds the thread released, removes the bar. Private frame, chrome, timeline and overlay factories preserve the original view hierarchy without adding component mount boundaries.

Timeline owners preserve initial-position identity, history anchors, search paging, unread receipts, gesture trimming and activation cleanup. Turn/protocol/content modules retain projection caches, bounded rendering and native reveal. Dependency rules forbid full workspace/composer/tool composition imports from detail, read surface, timeline, turns, protocol and content. Native keyboard geometry remains active while fullscreen coverage pauses tail following and paging.

Main selection still publishes cached content and hydrates history progressively. After the bottom chrome is measured, a nonempty data-ready timeline mounts behind the transcript boundary until LegendList reports `onReady`. An initial unread target is then measured against the usable viewport between the header and composer; any required nonanimated correction completes before the one-way per-chat reveal. The first completed agent turn that makes a thread unread owns this initial anchor across later completions and a trailing in-progress turn; tail-follow is admitted only when no unread anchor exists, and an explicit gesture or jump releases that anchor. The transcript skeleton appears only when loading or positioning exceeds 200 ms, and no refresh, unread or cursor state participates in this presentation gate. Persisted composer state is a progressive render resource: the canonical `ConversationLayout`, header and timeline mount immediately, while only the composer slot shows its geometry-preserving placeholder until restoration completes. Composer restoration precedes editing; the ready editor then stays mounted. Subagent selection retains its Transition and does not construct main editor/upload/queue-edit/voice bindings. JS runtime startup is separate from native boot and feature lifetime.

Validation: V1 gate (2422 modules, 9100 dependencies), history/projection/output/streaming and repaired source contracts, 21 render cases across five suites, Android/web Expo export. Actual device gestures, native retained view behavior and relative performance remain unverified. The final full Vitest run passes 2213 tests; completed final platform validation and device limits are recorded in the migration ledger.

`workspaceCapabilities.ts` is the public qualified scroll/history contract. The private `workspaceAdapter.ts` binds the shared ThreadUiState seed and existing thread-sync reads only from exact workspace composition; it creates no timeline cache.

Private composition seams: `activeConversationScope` resolves the destination; `ConversationDestinationSurface` renders its existing boundary; `mainConversationHistory` binds history resources and `MainConversationPublication` publishes cached snapshots. `conversationScopeFeatures` and `conversationSurfaceAssembly` compose the main editor/tools. `readConversationTimelineBindings` and `ReadConversationLayout` compose the subagent read surface. Timeline gesture/measurement callbacks retain `useEvent` and original ref handles. Turn user/agent body and protocol presentation factories preserve element order and reuse the coupled public ToolContent declarations. No factory adds mounted state or a fetch effect.

Turn content preparation is shared across physical timeline slices through a 64-entry working-set cache keyed by immutable TimelineItem identity. A new source snapshot invalidates preparation; search focus, fork availability and pending-request visibility are applied independently. Cache eviction changes work only, never visible content. Changes footer parsing happens on explicit open; it passes the latest recorded turn patch and qualified target to the existing shared viewer.

Every turn is its own agent bubble. A turn without a user message (a background task woke the agent) is never folded into a neighbouring turn: Claude answers each wake as a separate turn, and an earlier answer may hold a question for the person. Such a turn has no pre-turn lifecycle: all of its work is the response. A completed wake that produced nothing (`isEmptyWake`: no answer, activity or artifacts; unloaded content without Companion totals counts as unknown) draws no rows. Rows never depend on neighbouring turns, so the resident history range may begin or end at any turn. A running turn folds its current group of tool calls (`ActiveTurnActivity`) like the collapsed groups between its texts: one row with the whole group's count, which opens a sheet with every call of the group (including the start the render window keeps unmaterialized), plus only the calls running now (else the newest one). Its texts stay visible; thinking and subagent rows keep their own presentation. A tool call's body and output never draw in a bubble: every group of tool calls is one row that opens the activity sheet, in a running and a finished turn alike; a running turn's current actions and the pre-turn tool steps draw as the same step row as in the sheet, without a disclosure, and a press opens the step's full-screen output, else the sheet (`ToolCardPlacementContext`: `bubble` rows, `sheet` disclosure). A finished turn's history row still expands in place, showing the agent's intermediate messages and its tool groups as rows. Thread search matches only what the person and the agent wrote (user and agent messages, intermediate ones included), never a tool call, its output or turn metadata; a match opens a finished turn's history and nothing else. Background task reports (`codewideTaskNotification` items, parsed once in `rendering/taskNotifications.ts`) are never turn activity. A child agent's result for its parent arrives the same way (statuses include `interrupted`), never as a user bubble; a batched notice's valid `reports` entries each become one report sharing the item's delivery and kind, and its top-level summary fields are read only when no entry is valid. A wake turn draws the reports that woke it, and those that arrived while it answered, as one line outside the bubble in its lead row; a person's turn draws its mid-turn reports as that line after its bubble. Consecutive wakes that produced nothing merge their lines, and the run joins the next wake's line; only lines merge, never turn content. The line is a pill at most half the conversation's width with an avatar stack, a short label and a status. A pill of one report opens that report directly (an agent's thread or a command's output) and shows an opening failure under itself; a pill of several opens their list centered on it, above or below, whose rows open the same targets. Subagents still working are read from their own child threads' status, never inferred from parent items: while any works, a separate chip floats beside the live plan above the composer (`features/agents/WorkingSubagentsMenu`) and opens a list of them; the composer's subagent chip stays the entry to all subagents. Bubbles draw no launch chips: a launch is not a result. A command running in the background (`codewideBackgroundTask`, read through `@codewide/sync-client` `parseBackgroundCommand` in `protocol/backgroundCommand.ts`) is the one launch drawn, and outside the bubble: its turn's trailing task line (`turnSlice.trailingTasks`, after a person's mid-turn reports) holds one pill per such command (`turns/backgroundLaunches.ts`), the same `TaskNotificationLine` pill as a report — terminal avatar with a status dot, the agent's description of the command (else its shortened first line) and its state and time: `running · 3m` (advancing while shown), the total run once completed, `failed · …`, `stopped · …` (Claude settles a task whose process is gone as stopped), or a muted dot with `ended` for a state the Companion cannot tell (another provider, or an older Companion's id-only marker); the phone never shows "unknown". Pressing it opens the task's output. One element per task: the report of a command the shown history launched is not drawn again (`timelineRows` `withoutDuplicateTasks`; a wake whose only line it was draws nothing); agent and other reports keep their line, as does a command report whose launch is outside the shown range. A foreground command draws nothing. The Companion republishes the command item when the task's state changes; a sealed turn's content does not change, so each command's latest state lives in the turn's mutable metadata (`codewide.backgroundCommands`): a live patch advances it (an ended state is final), and every turn write, an authoritative read included, reconciles it with the states the read carries (`mergeBackgroundCommandStates`: the read's end wins, its running or unknown never replaces an end), so a lost live event is repaired by the next read without a reopen. The pill reads that metadata, else the item. Compact stored turns keep background commands resident. A merged reason line keeps its first wake's row key and date while later wakes join it. A background task opens by id: a command report's row, a background command's pill and its command block load the first page of its output through `companion/thread/backgroundTask/read` on press (`BackgroundTaskOutputHost`, mounted once per conversation frame) and only then open its output screen, a thread route like the full command output (`task-output/[sessionId]`, `BackgroundTaskOutputScreen`). Its header reads "Background command"; the command (or Claude's description of it) is pinned above the output as a prompt line, never the title. The screen reads the rest by itself (`followBackgroundTaskOutput`: remaining pages at once, the tail of a long output, a running task every 2 s until the screen closes) and shows it in a read-only Ghostty terminal (`TaskOutputTerminal`, the `readOnly` prop of our `expo-libghostty` patch) whose background is the viewport's, so it needs no frame; line feeds become CR LF as a TTY would write them. Web shows plain text instead. No output is shown inline. Context compactions (`contextCompaction` items) are system information, never turn activity, in any turn: they draw as lifecycle lines ("Compacting context", then "Context compacted") outside the bubble. A finished turn draws them in its lead row, the same for summary and full items. While a turn runs, a compaction after its first response item is part of that work: it joins the turn's activity inside the bubble (and the Companion's live activity counts), like any tool call; one before the response leads the bubble. A turn whose only content is compactions (`isCompactionOnly`, not failed or interrupted) draws just its lead row: no bubble, footer, thinking placeholder or empty-response text. Compact stored turns (`compactCompletedTurnForStorage`) keep reports and compactions resident, and a summarised wake without a report (an older Companion) is unknown, never hidden.

The Activity sheet is a recycling LegendList of fixed-height two-line Expo list rows. A row keeps the protocol icon, shows the server-projected output-token footprint followed by the concrete tool-call name, and marks failed calls in red. Rows have no disclosure chevrons and never expand inside the list: command, file, image, subagent and generic text output open their semantic destination directly; Web Search alone opens its explicit second results sheet; informational fallback rows stay inactive. The aggregate button that opens Activity uses a forward chevron. Older persisted expansion state cannot change either path.

Activity counters, output-token estimates and estimated input cost are server-owned projections. TurnMetricsProvider supplies validated figures; range selectors match exact item IDs and never derive totals from visible command output. Full activity hydration retains range metadata on its first item. Missing attribution stays unknown. See docs/android-activity-metrics.md for the versioned contract.

The aggregate `turnDiff` is footer-owned: the footer opens the whole turn in Changes. It is not an Activity step, is not included in Activity counters or ranges, and is never synthesized into the Activity sheet. A `fileChange` remains a concrete tool-call step and may open only the changes owned by that call.
