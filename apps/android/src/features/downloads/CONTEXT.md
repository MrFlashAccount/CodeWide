# V1 downloads

Public surfaces: `DownloadsSheet` lists this device's downloads by day, newest first, and exposes the Chrome-style per-file controls: pause, resume and cancel for unfinished downloads, retry for failed or cancelled ones started in this process, and open, remove from list and delete for completed files. The remembered download folder is a device setting: Settings shows and changes it in its Downloads section (`features/settings/DownloadSettings`), as Chrome keeps Download location in its settings rather than in the list. `useDownloadsActivity` projects overall progress of running downloads for an indicator outside the sheet; the thread-list menu draws it as a ring in place of its `⋮` glyph and leads to the sheet through its Downloads item.

Route composition owns the sheet's visibility and passes `openDownloads` to the thread-list headers, like the terminal manager. The feature reads the process `DownloadManager` (`data/downloadManager.ts`) through `DownloadManagerProvider`; it owns presentation only. It does not start transfers, persist history, pick folders or touch files itself: those remain the manager's and the native file layer's.

Unfinished downloads do not survive the app process: they reload as `interrupted`, with only Remove, because the transfer access lived in the previous process. Downloads run in JavaScript and can be throttled while the app is in the background; there is no system notification or foreground service. Physical-device verification of the Storage Access Framework folder grant across restarts, partial-file cleanup and background behaviour remains pending.
